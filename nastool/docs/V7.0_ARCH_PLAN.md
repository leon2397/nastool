## 三、V7.0 框架内核升级

> 目标：让诊断速度 60s → 15s，新增 check 成本降低 50%
> 工期：4–6 周
> 依赖：无（可独立推进）

### 3.1 异步并行执行引擎

**文件**：`core/executor.py`（新建）

**策略**：
```
Level 0: 全部串行（保留 fallback）
Level 1: 按 category 并行（AI/Storage/System/Network 各一个协程）
Level 2: 完整依赖图拓扑排序 + asyncio（默认）
```

**依赖图构建**：
```python
# 新增 checks/base.py 字段
@dataclass
class CheckMeta:
    depends_on: List[str] = []        # ["gpu_detected"]
    estimated_time: float = 0.5      # 秒，调度参考
    can_parallel: bool = True        # False 则强制串行
    timeout: int = 30                # 超时秒数
```

**具体改动**：

| 文件 | 改动 |
|------|------|
| `checks/base.py` | 新增 `CheckMeta` dataclass，`BaseCheck` 增加 `meta` 属性 |
| `checks/registry.py` | 改为 `check_registry` 类，构建 DAG，返回拓扑序 |
| `core/executor.py` | 新建：异步调度器，支持 Level 1/2，timeout 传播，early-exit（critical fail） |
| `core/executor.py` | fallback：Level 0 串行，无任何依赖包时走此路径 |
| `arm_diagnose.py` | 新增 `--parallel LEVEL` 参数，默认 `LEVEL=2` |

**预计效果**：82 check，Level 2 下 10–15s（GPU 类并行、网络类并行、系统类并行各一组）

### 3.2 Check 声明式重构

**文件**：`checks/base.py`（改）、88 个 check 文件（逐批迁移）

**目标**：减少 boilerplate，新增 check 从 ~60 行 → ~25 行

**Before（现状）**：
```python
class GPUDetectedCheck(CheckBase):
    name = "gpu_detected"
    category = CheckCategory.AI
    severity = CheckSeverity.WARNING

    def is_applicable(self, ctx) -> bool:
        return ctx.platform in [Platform.JETSON, Platform.ASCEND]

    def run(self, ctx) -> CheckResult:
        # 55 行实现...
```

**After**：
```python
@check(
    id="gpu_detected",
    category=CheckCategory.AI,
    severity=CheckSeverity.WARNING,
    platform=[Platform.JETSON, Platform.ASCEND],
    timeout=10,
)
def gpu_detected(ctx: CheckContext) -> CheckResult:
    """检测 GPU 是否被系统识别"""
    # 25 行实现...
```

**迁移策略**：按 category 分 7 批，每批 `git commit`，不停机：
```
Phase A: AI checks (17 个)        → 1 周
Phase B: NAS + Storage checks     → 1 周
Phase C: Network + System checks  → 1 周
Phase D: Security + USB checks     → 1 周
```

每个 check 改完后跑 `pytest tests/test_checks*.py` 回归。

### 3.4 Fix 引擎统一

**合并目标**：`fix_engine_v2.py` + `fix_recommendations.py` + `interactive_fix.py` → `fix_engine.py`（单文件）

**新架构**：
```
fix_engine.py
├── FixPolicy:     判定 check 对应的 fix 是否可执行
│   ├── check_fix_map  # from config
│   ├── is_applicable()  # 复用现有
│   ├── risk_assessment()  # 低/中/高/危险
│   └── requires_backup()  # 危险 fix 前自动备份
├── FixExecutor:   执行修复
│   ├── dry_run()
│   ├── execute(fix_id) → FixResult
│   └── rollback(fix_id) → bool
├── FixHistory:    执行历史（写入 history.jsonl）
└── InteractiveFix: 交互式选择（从 interactive_fix.py 迁移）
```

**新增 FixRollback**：
```python
# 每个 fix 注册回滚函数
fix_registry.register(
    "cleanup_docker_images",
    rollback=lambda ctx: restore_docker_images_snapshot(ctx.snapshot_id)
)
```

## 四、V8.0 高级特性

> 目标：重复诊断 15s → 2s，健康预警提前 48h
> 工期：3–4 周
> 前置：V7.0 完成

### 4.1 分层缓存

**文件**：`core/cache.py`（新建）、`data/`（重构）

```
data/
├── cache.sqlite          # TTL 分层缓存
├── history.jsonl         # 追加行（每次诊断一行）
└── snapshots/            # gzip 压缩快照（每周一次）
```

**缓存策略**：
| 数据类型 | TTL | 失效条件 |
|----------|-----|---------|
| SMART 健康 | 24h | 手动触发 invalidate |
| GPU 状态 | 1min | 同设备重复诊断 |
| 网络连通性 | 5min | 网络环境变化 |
| 系统版本 | 30min | 任意 |
| DNS 记录 | 10min | DNS change event |

### 4.2 健康分算法 V2

**文件**：`utils/health_scorer.py`（重构）

**改进**：
1. **动态基准**：Orin AGX vs Orin Nano 基线不同（CPU 利用率 / 内存上限），读 `profiles/jetson_devices.yaml` 动态基线
2. **权重贝叶斯**：上次异常 → 本次权重 ×1.5；连续正常 → 权重趋近 1.0
3. **趋势预警**：连续 3 次下降 → 发 `WARN` 级别预警（不等分数跌破阈值）
4. **异常波动检测**：单次下降 >20 分 → 自动触发深度诊断（跑 sub-category）

### 4.3 Web 健康报告

**文件**：`reporters/dashboard_reporter.py`（重构自 `health_dashboard.py`）

**改进方向**：
- 生成独立 HTML（无外部依赖 CDN offline 可用）
- 趋势图表用纯 SVG（不用 Chart.js）
- 增加：设备基线对比、Top 风险项、Fix 建议卡片

## 八、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| Check 并行化破坏时序依赖 | 结果错误 | Level 2 前先跑 Level 1 回归测试；`--parallel 0` 回退 |
| 88 个 check 逐个迁移量大 | 工期延误 | 按 category 分批，每批独立 commit，随时可回滚 |
| Pydantic 模型与 YAML 不兼容 | 启动报错 | 先写 YAML→Pydantic 反向生成脚本，两边对拍 |
| 缓存穿透（脏数据） | 误判 | TTL 设保守值 + 手动 invalidate 接口 |
| .git 仓库损坏 | 无版本控制 | 重建 .git；未来所有架构改动独立 branch |

## 九、快速启动建议

**下一步最优路径**（最小改动，最大收益）：

```
1. 新建 core/executor.py（异步引擎）
2. 在 arm_diagnose.py 中加入 --parallel 参数（不改现有 check）
3. 运行 pytest 验证串行/并行结果一致
   → 这 3 步完成后：诊断时间 60s → 15s，用户立竿见影感知改善
4. 再逐步重构 check 声明式（按 category 分批）
```

建议从 **AI checks**（17 个，平均 100 行，最复杂）开始试点，验证模式可行后再推广到全量。
