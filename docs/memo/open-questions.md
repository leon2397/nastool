## 开放中

### Q-001 要不要生成修复脚本（只生成，不执行）

**问题** 检测到 `nfs_root_squash` 缺失时，除了给建议文字，能不能直接输出一段可复制的命令？
再进一步，能不能生成一个 `fix.sh`（**不执行**，由用户自己 review 后跑）？

**为什么重要** 这是"体检"和"治疗"的分界线。[ADR-0007](../adr/0007-no-fix-engine.md) 明确
不做修复引擎，理由是"自动改配置会把可信工具变成危险工具"。但**只生成不执行**在不在那条
ADR 的禁令范围内，当时没想清楚。

**当前倾向** 倾向做，但只做"最小可见改动"：输出 `diff` 式的建议（原行 / 建议行），不给
完整脚本。理由是完整脚本会诱导用户 `sh fix.sh` 一把梭，而那等于把风险从工具转到用户的
判断力上——用户并不知道每一行改什么。

**做决定需要什么** 至少有一个真实用户场景表明"给建议文字不够用"。目前没有。

**决定后** 更新 ADR-0007 或新增一条。

### Q-002 上报失败要不要影响退出码

**问题** `--push webhook` 失败时，退出码仍是 `0`（报告本身生成了）。要不要加
`--push-required`，让上报失败返回非零？

**为什么重要** cron 场景下，用户希望"这台机器的结果没上报成功"能被发现。现在只能靠抓输出。

**当前倾向** 加一个可选开关 `--push-required`，默认关闭。默认行为不变（避免破坏既有的
自动化脚本），需要严格语义的人自己开。

**做决定需要什么** 确认没有既有脚本依赖"push 失败也返回 0"。目前没有外部使用者，随时可做。

**决定后** 写进 [CLI.md](../CLI.md)，不需要 ADR（不是架构决策）。

### Q-003 `report_version 3.0` 稳定后要不要承诺向后兼容

**问题** 现在是"字段增删改就升版本，消费者自己适配"。到某个时点，是否要承诺"3.x 只加字段、
不删不改"？

**为什么重要** 这会直接影响能不能做生态（第三方写报告解析器、接 BI）。没有兼容承诺，
没人敢深度集成。

**当前倾向** 等出现第一个真实第三方消费者再承诺。现在承诺只是给自己上枷锁，而字段可能还要
动（DEBT-002 的 `priority` 就会加字段）。

**做决定需要什么** 有一个外部消费者，或者 `1.0` 发布。

**决定后** 写 ADR，并更新 [OUTPUT.md](../OUTPUT.md) 顶部的兼容说明。

### Q-004 要不要开放第三方检测项（插件）

**问题** `@check` 注册表已经让"加一项检测 = 写一个函数"，能不能进一步允许外部包注册
自己的检测项（entry points）？

**为什么重要** 有些检测项高度垂直（某品牌的 UPS、某型号的硬盘笼、某个行业特定的合规项），
不该进主仓。插件是自然的解法。

**当前倾向** 暂不做。理由：`CheckContext` 是内部 API，一旦暴露就得保证稳定，而现在它还在
变（DEBT-001 会改采集层）。开放早了会锁死设计。

**做决定需要什么** 出现"想加检测项但代码进不了主仓"的真实需求，且 `context` 稳定 3 个月以上。

**决定后** 写 ADR，同时定义插件 API 的兼容承诺。

### Q-005 要不要支持多机批量体检

**问题** 一次检查多台设备（给一组 IP + 凭据，本地并发跑）。

**为什么重要** 这是"工具"和"系统"的分界。有它才能做小团队的资产盘点。

**当前倾向** **不做。** 一旦支持远程，就必然要处理凭据存储、SSH 密钥、失败重试、并发
限流——那就是另一个产品了。而且与底线二（不修改被检测设备）的边界会变模糊。
需要批量的人可以用 `ansible` 或 `pssh` 调 `nastool -o json`，结果自己汇总。

**做决定需要什么** 出现明确的批量需求，且愿意接受"不做远程执行、只做结果聚合"的形态
（即：用户自己把 nastool 发到各机器上跑，工具只提供 `nastool aggregate *.json`）。

**决定后** 写 ADR。倾向于只做聚合，不做远程。

### Q-006 跨设备的分数可以比较吗

**问题** 用户会问"我的 NAS 87 分，朋友的 92 分，谁的好？"

**为什么重要** 如果分数不可比，那就不该暗示可比。现在的权重是按"通用 NAS"设的，
一台 4 盘位家用机和一台 24 盘位企业机的 87 分含义完全不同。更麻烦的是覆盖度差异：
Linux 上判定 51 项得 87 分，Windows 上判定 20 项得 87 分，可信度差很远。

**当前倾向** 明确说"分数只在同一台机器的时间纵向上有意义，横向比较无意义"。报告和文档
都要写这句（[SCORING.md](../SCORING.md) 已有类似表述，需要强化）。

**做决定需要什么** 不需要新信息，这是个表述问题。倾向现在就定，写成"不承诺跨设备可比"。

**决定后** 这属于产品表述而非架构决策，写进 SCORING.md 即可。

### Q-007 `--only` 过滤后总分还有意义吗

**问题** `--only storage.* --only security.*` 只跑两个分类，其余分类 `judged=0` 不进加权，
总分实际等于这两个分类的加权平均。

**为什么重要** 用户可能拿这个分数当"整机健康度"，但它只反映了选中的那部分。而且此时
盲区计算的分母也变了（只算选中的项），封顶规则可能不触发。

**当前倾向** 保留现行为，但在报告里显式标注"本报告仅包含 N 类 M 项，总分不代表整机健康度"。
不加额外机制——过滤本来就是"我只想看这块"。

**做决定需要什么** 确认没有用户把过滤后的分数当全量结论。这需要看真实使用。

**决定后** 只需改报告文案 + [CLI.md](../CLI.md)。

### Q-008 历史库默认放哪

**问题** 现在是 `~/.nastool/history.db`（用户主目录）。对 NAS 用户，主目录常在小容量 DOM 盘上。
要不要改成报告输出目录旁边，或者当前工作目录？

**为什么重要** 主目录方案的问题：① 空间；② 换用户跑就看不到历史；③ 备份难找。
当前目录方案的问题：每次在不同目录跑就分裂成多个库。

**当前倾向** 保持 `~/.nastool/`，但 `--history-db` 的文档要写清"建议放到数据盘"。
理由：默认值必须让"什么参数都不给"也能工作，而当前目录不可靠。

**做决定需要什么** 至少一个真实用户反馈"主目录放不下"。

**决定后** 不需要 ADR。

### Q-009 输出要不要国际化

**问题** 报告正文、CLI 帮助全是中文。要不要做 i18n？

**为什么重要** 如果这个工具要开源给非中文用户，这是硬门槛。检测项标题（`title`）也是中文，
写进了报告 JSON。

**当前倾向** 暂不做，但**避免把中文写进契约字段**：`CheckResult.id`、`Status` 值、分类键
都已是英文，这是对的；`title` 和 `summary` 是中文，属于展示层。将来要国际化，需要给
`title` 加一份英文映射，而 `summary` 是运行时拼的字符串，改造代价大。

**做决定需要什么** 有非中文用户的实际需求。

**决定后** 写 ADR，重点是"哪些字段属于展示层、哪些属于契约"。

### Q-010 Windows 支持做到什么程度

**问题** 现在 Windows 上大量检测项 SKIP，能判定的项明显少于 Linux。要不要补齐？

**为什么重要** 关系到 [DEBT-010](debt.md#debt-010-windows-支持深度不足) 的优先级，也关系到
AINAS 的 Windows 客户端形态。

**当前倾向** 优先保证"能跑、不误报、说清限制"，而不是"项数对齐"。Windows 用 `Get-*` 系列
能拿到的东西不少，但每加一项都要真机验证，成本高。

**做决定需要什么** 先看清 Windows 用户的实际用途（当 NAS 用？还是只当检测工作站用？）。
这决定了要不要为它做 RAID/存储栈的深度采集。

**决定后** 写 ADR，并更新 [PROFILES.md](../PROFILES.md)。
