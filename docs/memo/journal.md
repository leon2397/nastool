## 2026-10-28 · 置信度参与判定（v0.4.0，DEBT-009 闭环）

**做了什么** 置信度从展示值变成判定依据。规则收在 `model.CheckResult.counts_toward_score`：
低置信（≤ 0.5）的 PASS 不进分母且计入盲区，低置信的 WARN/FAIL **仍然计入并照样触发封顶**。
覆盖度新增 `low_confidence` / `usable` / `usable_percent`，`blind_percent` 改为
`(unknown + low_confidence) / applicable`。`report_version` 3.0 → 4.0，
`diff.py` 检测跨口径对比并**不给差值**。新增 ADR-0009、18 项专属测试。

**为什么** 与原计划两处不同，都是防漏报：
① 阈值改 `<= 0.5`——多源冲突时置信度**恰好落在 0.5**，严格小于会把唯一能产出
低置信判定的那一类全漏掉；② 改成 PASS/FAIL **非对称**——对称处理会让低置信的 FAIL
被从分数里抹掉，不再扣分也不再封顶，等于让设备看起来比实际更健康。
这与「温度取 MAX 而非平均」是同一条安全保守逻辑。

**验证** 新增 `tests/test_debt009_confidence.py` 18 项；变异测试四种劣化
（对称处理 / 阈值严格小于 / 低置信不计盲区 / 去掉口径检测）**全部被精确捕获**；
六条既有不变式仍全绿。

**遗留** DEBT-014（内存与 SMART 第二来源）是 0.4.0 的最后一项。

## 2026-10-28 · 产品化规划（v0.3.4，0.4.0 前置）

**做了什么** 新建 [PRODUCT-PLAN.md](../PRODUCT-PLAN.md)：目标用户与三条用户旅程、交付形态矩阵、
成熟度阶梯 L0–L2、信任机制缺口、成功度量、8 条风险登记、商业化路径、行动顺序。
同时补齐产品化的法律与打包基础：新增 `LICENSE`（MIT 正本）、`MANIFEST.in`（排除 `reference/`）、
`pyproject.toml` 改 SPDX license 写法。登记 DEBT-015/016/017 与 Q-011/Q-012。

**为什么** 版本计划管"什么时候改代码"，产品化规划管"这东西长成什么样"——混在一起会出现
"版本号到 1.0 但产品不可用"。核实过程中发现 README 声明 MIT 但**仓库里根本没有 LICENSE 文件**
（`git log --all -- LICENSE` 为空），这是法律基础缺失。

**关键判断** ① 价值主张是"结论可信"不是"检测项多"，产品化投入全部指向"让用户能验证结论"；
② 成熟度**止步 L2**（可被依赖），不做 L3 生态——插件 API 一旦公开就要背兼容承诺，
而检测工具的生态价值低；③ 商业化走纯开源，不做 SaaS（上传数据会毁掉"离线可跑"这个优势）；
④ 容器镜像优先级压低——容器内读不到宿主机传感器，与"结论可信"天然冲突。

**验证** selfcheck 新增第 13 项"产品化规划一致"（双向引用 + 规划里的债/问题必须已排期 +
LICENSE 必须存在），13/13 绿；pytest 54 passed；`python -m build --sdist` 实测通过，
产物含 LICENSE、不含 reference、无 setuptools 弃用警告。

**遗留** 远端仓库与 CI 未建（需用户账号，DEBT-016）；单文件可执行版待实测体积（Q-011）。

## 2026-10-28 · 多源数据融合（v0.3.4，0.4.0 第一步）

**做了什么** 新增 [fusion.py](../../nastool/fusion.py)：5 种融合方法、一致性验证、测量点归一化、
按量纲分列的容差表。温度采集改为 hwmon 与 thermal_zone **两个来源都读**并标注 `source`；
`system.thermal` 改为跨测量点取 MAX、同测量点做交叉验证，差 > 5°C 报「温度读数存在争议」
并降置信度到 0.5。报告层（终端 + HTML）标注置信度 < 0.7 的判定项为「⚠ 结论存疑」。

**为什么** DEBT-001：旧实现 hwmon 有值就不读 thermal_zone，而两者在 ARM 板子上能差 15°C，
取哪个直接决定告警与否，用户却看不出有争议。前身项目有这套机制但代码已丢失，只剩 API 文档。

**关键决策** 融合放判定层不放采集层（采集保留多源是「事实的完整性」，不违反 ADR-0002）；
温度用 MAX 不用平均——平均会低估散热风险；先归一化测量点，否则「CPU 45 + GPU 70」会被
误判成矛盾产生假告警。见 [ADR-0008](../adr/0008-multi-source-fusion.md)。

**验证** 新增 `tests/test_fusion.py` 23 项，并用**变异测试**证明这些测试有牙齿：MAX 改成平均、
归一化全部映射到 cpu、冲突仍返回 PASS——三种变异均被精确捕获。selfcheck 12/12 绿，
pytest 54 passed，端到端 51 项 / 8.4s / exit 0。

**遗留** 内存与 SMART 仍是单来源（DEBT-014，新登记）；下一步做 DEBT-009 置信度参与判定。

## 2026-10-28 · 架构重建（v0.3.0，破坏性）

**做了什么** 判定内核重写为四层：契约（`model.py`）→ 注册表（`@check`）→ 采集（`collect/`，
只拿事实）→ 判定（`checks/`，55 项）→ 聚合（`scoring.py`）→ 呈现（`reporters/`）。
删除 `core/` 与 `adapters/`，`report_version` 升 3.0。

**为什么** 0.2.0 加一项检测要改五个地方（采集、评分、终端、JSON、HTML），逻辑复制多份，
结论容易互相矛盾。用户明确要求"不要一步一步改，先把产品架构重新建立起来"。

**三条不变式落地** UNKNOWN 成为一等状态（读不到 ≠ 坏掉）；两条封顶规则（有 FAIL → 59；
盲区 ≥50% → 74、≥30% → 84）；覆盖度分母改为适用项（此前 Windows 上被误算成 39%）。

**顺手修的 bug** `connectors/ainas.py` 仍在读 2.0 的顶层 `device`/`storage`/`ai_accelerator`，
格式升级后推送的设备信息会全空。加 2 条契约测试锁住。

**验证** pytest 30 passed；Windows 真机 51 项 / 7.5s / exit 0；不存在路径 → exit 1 / 59 分 D。
