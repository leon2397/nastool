# 技术债

> 每条必须写清 **不修的代价** 和 **触发条件**（什么情况下必须修）。只写"待优化"的债
> 等于没有优先级，永远不会被修。
>
> 编号永久保留，修掉后标 ✅，正文不删——留下"我们曾经这样欠着"的记录。
> 规则见 [README.md](README.md)。

## 未修

### DEBT-002 建议是单条的，没有行动计划

**现状** WARN/FAIL 的 `suggestion` 是一句话，平铺在报告里。20 项告警就是 20 条并列的建议，
用户看不出先做哪个。

**不修的代价** 前身的 `action_plan` 带 `priority` 与 `risk`（修这个动作本身有多大风险）。
没有它，"体检报告"就停在诊断，用户还得自己判断"先修 Telnet 还是先换硬盘"。而这两件事的
紧急程度差一个数量级。

**触发条件** 报告要给非技术用户看时（例如交付给买了成品的家庭用户），或者 `verify` 场景
被用于验收流程。

**修法要点** `CheckResult` 加 `priority`（0–3）与 `fix_risk`（低/中/高），由判定项自己声明
——判定项比评分器更清楚这件事多急。报告器按 priority 排序生成"建议做什么"章节。

**规模** 中。契约加字段 + 55 项各标一次 + 三个报告器。

### DEBT-003 服务只探端口，不验协议

**现状** `services.*` 全部基于"端口在听"。445 在听就认为 SMB 可用。

**不修的代价** 这是当前与"通用 NAS 工具"最实质的差距。真实故障里有一整类：进程活着、
端口在听、但协议握手失败（SMB 版本协商不过、NFS 未导出、TLS 证书过期导致 Web UI 打不开）。
现在的报告会说"文件共享服务正常"，而用户此刻连不上。

**触发条件** 有用户反馈"报告说正常但我连不上"，或者开始做远程运维场景。

**修法要点** 加只读的协议探测：SMB 发 `SMB2 NEGOTIATE`、NFS 查 `showmount -e`、HTTP 取
`/` 头、SSH 读 banner。**必须严格只读**（底线二），不认证、不写。作为独立检测项
（`services.smb_handshake` 等），不替换端口检查。

**规模** 大。每个协议一个探测实现，且要考虑超时。

### DEBT-004 单项超时只在 POSIX 生效

**现状** `RunOptions.check_timeout`（60s）靠 `signal.SIGALRM` 实现，
Windows 上 `hasattr(signal, "SIGALRM")` 为假，整段跳过（`engine.py:55`）。

**不修的代价** Windows 上某项检查卡住（例如 `smartctl` 对某个 USB 桥接盒无响应）会挂住整次
运行，用户看到的是"程序没反应"，没有任何提示。

**触发条件** Windows 上出现"跑到某一项就不动了"的反馈，或者 Windows 客户端化。

**修法要点** 用线程 + `join(timeout)` 包一层（检查函数是纯 CPU/IO，不强求主线程），
或者对每个外部命令用 `subprocess(timeout=)` 统一收口。前者改动小，代价是无法真正杀死
卡住的线程（只能放弃等待）。

**规模** 小到中。

### DEBT-005 历史库不会自动清理

**现状** `HistoryStore.prune()` 存在，但只能通过 `--prune-history DAYS` 手动触发。

**不修的代价** 每条记录存完整报告 JSON（真机约 60–120 KB）。每天跑一次，一年约 30 MB，
三年 100 MB。不算灾难，但 NAS 用户的 `~` 分区经常是小容量 SSD 或 DOM 盘。

**触发条件** 用户把 nastool 挂进 cron 每天跑时。

**修法要点** `save()` 时顺带检查条数与总大小，超过阈值按最旧优先删，并打印一行提示。
阈值可配置，默认保留 365 天。

**规模** 小。

### DEBT-006 分类一致性没有运行时校验

**现状** `CATEGORY_ORDER` 在 `model.py`，权重在 `profiles.py` 手写 dict。新增分类若忘了改
`profiles.py`，该分类权重取默认 0、且不在任何 `active` 里 → **静默不检测**，没有任何报错。

**不修的代价** 加一个分类、写完 8 项检查、跑测试全绿、发版——然后发现这 8 项从来没被执行过。
`selfcheck` 现在会比对键是否合法，但只在开发时跑，运行时不校验。

**触发条件** 第一次新增分类时（就是下一个 DEBT-002 之后的动作）。

**修法要点** 在 `profiles.py` 加一次性校验：每个 profile 的 `weights` 键与 `active` 都必须
⊆ `CATEGORY_ORDER`，导入时抛 `ValueError`。或者更彻底——从 `CATEGORY_ORDER` 生成默认权重。

**规模** 小。

### DEBT-007 没有系统盘空间检查

**现状** `storage.capacity` / `storage.inode` 只检查 `--storage-path` 指向的数据盘。

**不修的代价** NAS 上最常见的故障之一恰恰是**系统盘满**：日志写爆 `/var`、Docker 镜像堆满
`/`、`/tmp` 塞满导致服务起不来。这类故障和"数据盘还有 40%"可以同时成立，而报告显示一切正常。

**触发条件** 有用户反馈"系统起不来但你的报告说健康"。

**修法要点** 加 `system.disk_root`（检查 `/` 与 `/var`、Windows 的 `C:`），阈值比数据盘更严
（系统盘 85% 就该告警）。注意容器内 `/` 是 overlay，要标 SKIP 或 UNKNOWN。

**规模** 小。

### DEBT-008 `tags` 是死字段

**现状** `@check(tags=[...])` 被声明、被存进元数据，但**从不参与任何筛选**。实际的场景筛选
靠 `Profile.active`（按分类）。

**不修的代价** 读代码的人会以为 `tags=["slow"]` 能实现"跳过慢检查"，实际不能。这就是"注释
撒谎"的变体——字段名暗示了一个不存在的能力。已在 `registry.py` 注释里标明现状，但字段还在。

**触发条件** 有人想按 tag 筛选时（例如"只要安全相关的项"）。

**修法要点** 二选一：要么实现 `--tag` 筛选（10 行），要么删掉字段。倾向于实现——"只跑安全
相关项"是真实需求，用 `--only security.*` 表达需要知道分类名。

**规模** 小。

### DEBT-009 置信度只是展示值，不参与打分

**现状** 每项有 `confidence`，报告汇总一个加权平均。但 `_category_score()` 不乘它，
低置信度的 PASS 与高置信度的 PASS 得分完全相同。

**不修的代价** 会给人一种"我们已经考虑了数据可靠性"的错觉。实际上一个靠猜得出 PASS 的项
和一个从内核直接读到的 PASS，对分数贡献一样。真正该做的是"低置信 → 不计入或降权"。

**触发条件** DEBT-001 修完之后（有了真实的多源判断，置信度才有意义）。

**修法要点** 不要简单地乘权重——那会让"读不到"变成"少扣点分"，反而更糟。更合理的是：
置信度 < 0.5 的判定不计入分母（等同 UNKNOWN 处理），只做展示。

**规模** 中。改评分逻辑必须重跑六条不变式测试。

### DEBT-010 Windows 支持深度不足

**现状** 55 项里有相当一部分 Linux 专属（`/proc`、`sysfs`、`ss`、`mdadm`、`smartctl` 路径），
Windows 上标 SKIP。实际能判定的项明显少于 Linux。

**不修的代价** 报告在 Windows 上覆盖度低，触发盲区封顶，用户看到 B/C 级却不知道为什么。
虽然报告会标"本平台有 N 项不适用"，但体验仍是"半成品"。

**触发条件** 要做 Windows 客户端（AINAS 四形态里的一条线）时。

**修法要点** 为 Windows 补对应的等价采集器：`Get-PhysicalDisk` / `Get-Disk`（RAID 与健康）、
`Get-NetAdapter`（链路）、`Get-SmbShare`、事件日志。`collect/` 已按平台分派，加实现即可。

**规模** 大。

### DEBT-011 没有自检命令

**现状** 装完之后如果行为异常（全是 SKIP、全是 UNKNOWN），用户只能靠
[TROUBLESHOOTING.md](../TROUBLESHOOTING.md) 手工排查。

**不修的代价** "为什么全是不可判定"是最高频的支持问题。让用户跑 15 条诊断命令不现实。

**触发条件** 第一次收到安装类问题反馈时。

**修法要点** `nastool --self-test`：检查 Python 版本、必需命令是否存在（`lsblk`/`smartctl`/
`ss`）、权限（能否读 SMART）、各采集器能否返回非空，输出一张"哪一环断了"的表。
**不评分、不产生报告**，纯粹是环境体检。

**规模** 中。

### DEBT-012 `reference/` 目录不进构建但占体积

**现状** `reference/legacy/` 存着前身项目的原始文档与代码片段，约 7 MB，不参与打包。

**不修的代价** clone 变慢、搜索结果被无关代码污染（`grep` 时经常命中前身实现）。

**触发条件** 仓库要公开或 CI 要跑全仓扫描时。

**修法要点** 保留结论（已提炼进 `CHECKS-ROADMAP` 与 `DESIGN-NOTES`），把原始代码移到
单独的 `nastool-reference` 仓库或 git 的一个 tag 上。若决定保留，在 `.gitattributes` 里
标 `linguist-vendored` 让统计忽略。

**规模** 小。

### DEBT-013 一半的坑没有守门测试

**现状** [gotchas.md](gotchas.md) 里 14 条有 6 条标了 ⚠️ 无守门：GOTCHA-002（Windows 防火墙
CSV）、003（GBK 解码）、007（全 SKIP 文案）、010（罕见分支 `NameError`）、012（上报失败与
退出码）、013（`SIGALRM` 平台判断）。

**不修的代价** 这六条里有四条是**已经踩过一次的**。没有守门就等于允许再踩一次。尤其 002/003，
它们只在 Windows 上出现，而开发主环境是 Windows——重写采集层时很可能再犯。

**触发条件** 下一次改 `collect/` 层的 Windows 分支时。

**修法要点** 把 PowerShell/命令输出存成**固定的文本 fixture**，让解析函数单独可测
（不依赖真机）。`tests/test_parsers.py` 已经是这个模式，照它写即可。GOTCHA-007 的文案
可以让终端报告器输出走一层"结论短语"函数，直接断言字符串。

**规模** 中。主要成本是收集 fixture。

### DEBT-014 内存与 SMART 仍是单来源

**现状** DEBT-001 修复后，温度已实现多源融合（两个来源都采集 + 一致性验证）。但另外两个
常见事实仍然是单来源：

| 事实 | 当前唯一来源 | 可加的第二来源 |
|---|---|---|
| 内存总量/可用量 | Linux `/proc/meminfo`；Windows WinAPI `GlobalMemoryStatusEx` | `sysinfo` 命令、`/proc/meminfo` 与 `MemTotal` vs `MemFree+Buffers+Cached` 交叉 |
| SMART 健康 | `smartctl`（需 root） | NVMe 可用 `nvme-cli`；SATA 可用 `hdparm` 交叉 |

**不修的代价** 这两类都是**单点故障**——来源读错或读偏时，报告给出一个看起来确定的数字，
用户无从察觉。内存尤其危险：容器里 `/proc/meminfo` 报的是**宿主机**内存，
`used_percent` 可能算出一个完全误导的百分比。

**触发条件** 出现「容器里内存占用显示 95% 但机器明明很空」这类反馈，或接入 NVMe 支持时。

**修法要点** 融合机制已就位（`nastool/fusion.py`），加第二来源的成本主要是采集侧：
`collect/` 里多采一路并标注 `source`，判定项改用 `fuse()` + `validate()`。
注意内存的 `available` 在不同内核版本口径不同（是否含 `Cached`），融合时要用**同一口径**
的两个数，否则会自己制造假矛盾。

**规模** 小到中。机制已备，主要是各平台的第二来源实现。

### DEBT-015 缺 LICENSE 文件

**现状** `README.md` 结尾写"MIT License"，`pyproject.toml` 里 `license = { text = "MIT" }`，
但**仓库里没有 LICENSE 文件**——`git log --all -- LICENSE` 为空，从未提交过。

**不修的代价** MIT 是一份"授权方必须明示许可条款"的许可。缺了正本，
别人无法确认这个项目"以 MIT 授权"——这不是形式问题，是**法律基础缺失**。
想被安装、被二次分发、被别人写进自己的产品里，都缺这一步。

**触发条件** 立刻。补一个文件，5 分钟，没有理由拖。

**修法要点** 加 `LICENSE`（MIT 全文，版权人写项目作者），并在 `pyproject.toml` 里
改用 `license-files` 指向它（PEP 639 写法），避免两处各写一份、年份不同步。

**规模** 极小。

### DEBT-016 没有 CI

**现状** 仓库里**没有任何 CI 配置**（无 `.github/workflows`）。`selfcheck` 12 项与
`pytest` 54 项全靠人手动跑。

**不修的代价** 规范里的"提交前跑 selfcheck + pytest"是纪律，纪律会松懈。
更实质的问题是：这是 L2 门槛第 5 条（见 [PRODUCT-PLAN.md](../PRODUCT-PLAN.md)），
没有 CI 就永远达不到"能被依赖"。而且 Windows 上的问题（[GOTCHA-002](gotchas.md)、
[GOTCHA-003](gotchas.md)）只有 Windows runner 才测得到。

**触发条件** 建远端仓库时（本来就要建），顺手接上。

**修法要点** GitHub Actions，一个工作流，两个 job：`selfcheck`（含文档一致性检查）
与 `pytest`。矩阵跑 `ubuntu-latest` + `windows-latest`——Windows 矩阵是必须的，
本机开发环境是 Windows，但这不等于测过 Windows 下的路径组合。

**规模** 小。

### DEBT-017 报告缺设备身份字段

**现状** 报告里没有设备序列号、资产编号、主机名以外的任何身份标识。
二手验机场景下，用户拿到一份报告，无法证明"这份报告说的是这台机器"。

**不修的代价** [PRODUCT-PLAN.md](../PRODUCT-PLAN.md) 里"二手买家"这条旅程的终点
是"导出报告当凭证"，而没有身份字段的报告**在交易争议里没有证据价值**。
同理，任何需要归档"这台机器当时什么状态"的需求都不成立。

**触发条件** 有人真的用 `verify` 场景做交易验收。

**修法要点** 采集层加"设备身份"事实（序列号优先，退化到主板/资产号/主机名），
写进报告顶层。**注意采集不到时不能报错**——很多设备不提供序列号，那属于 UNKNOWN
而非 FAIL。身份字段属于**契约字段**，要进 [OUTPUT.md](../OUTPUT.md) 并考虑
`report_version` 升级。

**规模** 小到中。

## 已修

### ✅ DEBT-001 多源数据只有回退，没有融合

**曾经的现状** 温度采集是 hwmon 优先、`thermal_zone` 兜底——hwmon 有值就完全不读 thermal_zone。
同一个事实有多份数据时，代码**取第一个成功的，不做交叉验证**。

后果：某些 ARM 板子的 hwmon 只报 SoC 某一点，thermal_zone 报整机热点，两者能差 15°C，
取哪个直接决定告警与否，而用户从报告里看不出"这个温度可能有争议"。

**怎么修的**（v0.3.4）

1. 新增 `nastool/fusion.py`：通用融合引擎，4+1 种融合方法、容差表、测量点归一化
2. 采集层改为**两个来源都读**并标注 `source`（不再互斥兜底）
3. 判定层 `system.thermal` 接入一致性验证：
   - 同测量点极差 > 5°C → WARN「温度读数存在争议」，detail 列出两个来源与差值
   - 跨测量点取 **MAX**（不取平均——平均会低估散热风险）
   - 矛盾时置信度降到 0.5，报告里显示「⚠ 结论存疑」
4. 报告层（终端 + HTML）统一标注低置信度判定项

**留下的教训**

- **「取第一个成功的」不是「融合」**。前者是 fallback，后者要回答「这些来源互相印证吗」。
- **平均值在温度这类量上是错的**，不是不够好，是语义错。取最高才安全。
- **归一化必须先做**。把 CPU 45°C 与 GPU 70°C 误配成"同点分歧"，会产生假告警——
  比漏报更糟，用户会为一个不存在的问题拆机器。

**延伸** [ADR-0008](../adr/0008-multi-source-fusion.md)。融合机制可复用到 NVMe
（`smartctl` vs `nvme-cli`）等其他多源事实。

**仍未做** 内存（`/proc/meminfo` vs `sysinfo`）与 SMART（`smartctl` vs `nvme-cli`）
仍是单来源。见 DEBT-014。

### ✅ DEBT-000 加一项检测要改五个文件

**曾经的现状** 0.2.0 里新增一项检测要改：采集器、`scoring.py`、终端报告器、JSON 报告器、
HTML 报告器。逻辑复制五份，任何一份漏改就出现"终端说 3 个问题、JSON 说 4 个"。

**怎么修的** 0.3.0 架构重建：`@check` 注册表 + `Evidence` 统一证据格式 + 报告器只接 `Report`。
现在加一项检测 = 写一个函数。

**留下的教训** 重复的不是代码，是**判断**。只要"什么算问题"这件事被复制，就一定会分叉。
