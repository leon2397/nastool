# 备忘录

> 干活时的记忆。**不是给人看的文档，是给下一个人（很可能是三个月后的自己）用的。**
>
> 一条硬标准：写下的话必须能让读者**做出决定**。做不到就别写。

---

## 为什么要有这套东西

这个项目已经吃过两次"记忆丢失"的亏：

- 前身项目（v7.1.0-beta）的代码内核丢失了，只剩文档，于是 92 项检测的实现细节全部蒸发，
  只能靠重写。**记下来的只有设计，没记下来的全没了。**
- 0.2.0 到 0.3.0 之间修的一堆 bug，原因散落在提交信息和我的临时判断里。等到重写采集层时，
  "Windows 防火墙 CSV 带引号"这个坑又被踩了一次——因为当时没写下"为什么会错"。

所以四本台账，各记一类东西，互不重叠：

| 台账 | 回答 | 什么时候写 | 什么时候销 |
|---|---|---|---|
| [journal.md](journal.md) | **发生了什么** | 每次实质性变更，收尾时 | 永不销（按季度归档） |
| [debt.md](debt.md) | **欠了什么** | 发现"这里不理想但先这样" | 修掉后标 ✅ 并留一行结论 |
| [gotchas.md](gotchas.md) | **炸过什么** | 踩坑并解决后，**当天** | 永不销（这是最贵的资产） |
| [open-questions.md](open-questions.md) | **还没定什么** | 遇到需要取舍但当下不必定的事 | 定了 → 写 ADR → 这里标关闭 |

第五本不在这个目录：**[adr/](../adr/)** 记"定了什么、为什么、放弃了什么"。它比这四本正式，
因为它约束未来的选择；这四本只记录过程。

## 一条信息该记哪里

```
这件事已经过去了（做了什么 / 验证了什么）
    → journal.md

这件事还没做，而且不做会有代价（缺能力 / 走捷径 / 已知不完善）
    → debt.md

这件事错过一次，可能还会错第二次（反直觉的坑、平台的怪行为、命令的陷阱）
    → gotchas.md

这件事需要做决定，但现在信息不够或优先级不够
    → open-questions.md      定了之后 → adr/

这件事是个取舍决定，且会约束以后的做法
    → adr/（正式） + journal.md 提一句（过程）
```

**同一件事可以同时进两本，但角度必须不同。** 例如"多源融合没做"：
`debt.md` 记它欠着、代价多大、什么条件下必须修；`open-questions.md` 记"要不要现在做、
还是先补别的"，如果最后决定"先不做"，那个决定进 `adr/`。

## 写法

### 通用

- 每条都有**编号和日期**，编号永久不复用（`DEBT-007` 修掉后仍然占位）
- 一句话说清是什么，不要铺陈背景
- **写验证方式**。"已修"不值钱，"用 `pytest -k cap` 证明"才值钱
- 涉及取舍的，写清"不这么做的代价"

### 各本的特殊要求

| 台账 | 必须有 | 常见错误 |
|---|---|---|
| journal | 做了什么 / 为什么 / 验证 / **遗留** | 只写做了什么，不写遗留 → 下一个人不知道从哪接 |
| debt | **不修的代价** + **触发条件**（什么情况下必须修） | 只写"待优化" → 没有优先级，永远不会被修 |
| gotchas | 现象 / 根因 / 规避 / **守门**（哪条测试或脚本防止复发） | 只写"要注意 X" → 三个月后照旧踩 |
| open-questions | 问题 / 当前倾向 / **做决定需要什么** | 只列问题 → 变成许愿池 |

"守门"这一列是 gotchas 的关键。一个坑如果只写在文档里，它还是会被踩；只有变成一条
失败的测试或一个自检规则，它才算真的被堵住。没有守门的坑要在 `debt.md` 里补一条
"给 GOTCHA-00x 加守门测试"。

## 生命周期

| 动作 | 频率 | 做什么 |
|---|---|---|
| 写 | 每次实质性变更 | 至少写 journal；遇到坑/债/问题顺手记 |
| 复查 | 每次发版前 | 过一遍 `open-questions.md`，看有没有到该定的时候了 |
| 清理 | 每季度 | journal 超过一季度的条目压成一段摘要；debt 里已修但没销的补齐；gotchas 检查守门是否还在 |
| 归档 | journal 超过 300 行 | 移到 `journal-YYYY-QN.md`，主文件只留最近一季 |

**不要定期清理 debt 和 gotchas 的"已解决"条目。** 它们记录了"我们曾经这样错过"，
删掉就等于允许再错一次。已解决的标 ✅，正文保留。

## 维护成本的控制

这套东西唯一的风险是**重到没人愿意写**。对策：

1. **journal 一条不超过 8 行。** 超过说明你在写文档，那应该去 `docs/`。
2. **只有模板才会没人填。** 每条都写实的事，不要留空占位符。
3. **不追求完整。** 漏记一条备注，比因为"要记全"而一条都不记好。
4. `selfcheck` 会检查台账编号连续、没有重复编号，防止手工维护出错。
