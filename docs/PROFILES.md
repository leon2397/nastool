# 检测场景（profile）

> 同一台机器，用途不同，「健康」的定义就不同。
>
> 一个只做文件存储的 NAS 不应该因为没装 PyTorch 被判为不健康；
> 一台 AI 推理盒子没有加速器则是实打实的问题。
>
> 相关：[SCORING.md](SCORING.md)（权重如何参与计算）、[CHECKS.md](CHECKS.md)（每项阈值）

---

## 1. 场景决定两件事

| 决定 | 由什么控制 | 效果 |
|---|---|---|
| **检测哪些分类** | `Profile.active` | 不在 active 里的分类，其检查项**根本不执行**（不浪费时间） |
| **怎么算分** | `Profile.weights` | 权重 > 0 才计入总分 |
| **判定阈值多严** | `Profile.thresholds` | 磁盘 80% 还是 90% 告警，取决于用途 |

注意「检测」与「计分」是两件独立的事：

- 不在 `active` 里 → 不检测
- 在 `active` 里但权重为 0 → **会检测、会展示，但不进总分**（`verify` 场景下的 `ai` 就是这样）

## 2. 四个场景

### `nas` — 存储服务器（默认）

> 家庭 / 小型办公 NAS：以数据安全与可用性为核心

| 分类 | 权重 | 主题 |
|---|---:|---|
| 存储 | 34 | 主体 |
| 网络 | 18 | 访问速度 |
| 系统与硬件 | 16 | 稳定性 |
| 服务与端口 | 16 | 职能是否正常 |
| 安全 | 10 | 暴露面 |
| 外设 | 6 | USB 硬盘盒等隐患 |
| AI | — | **不检测** |

阈值：磁盘 80/90、内存 85/95、温度 75/88

不检测 AI 是刻意的：纯存储用途无需算力，检测了只会制造无关噪音。

### `verify` — 二手验机

> 买机器前验收：重点看硬件损耗、是否被改过、隐藏风险

| 分类 | 权重 | 与 `nas` 的差异 |
|---|---:|---|
| 存储 | 32 | 略降 |
| **安全** | **18** | **从 10 提到 18**——买家最关心「有没有被留后门」 |
| 系统与硬件 | 14 | 略降 |
| 网络 | 12 | 降（验机不关心外网） |
| 服务与端口 | 14 | 略降 |
| 外设 | 6 | 不变 |
| AI | 0 | **检测但不计分** |

阈值放宽：磁盘 85/95、内存 90/97、温度 80/92

**放宽阈值是刻意的**：验机时看到的是一台「还没配置好、可能满载跑着压力测试」的机器，用生产环境的严格阈值会误报一堆问题。真正该盯的是硬件损耗（`smart_age`、`smart_bad_sectors`）和配置隐患（`ssh_root_login`、`smb_guest`、`nfs_root_squash`）。

AI 检测但不计分：万一卖家号称这是 AI 盒子，你需要知道真相，但这不该影响机器的整体评分。

### `dev` — 开发机 / 虚拟化宿主

> 开发机、软路由、Proxmox 宿主：关注负载、网络与系统状态

| 分类 | 权重 |
|---|---:|
| 系统与硬件 | 20 |
| 存储 | 20 |
| 网络 | 18 |
| 安全 | 18 |
| 服务与端口 | 14 |
| AI | 10 |

阈值最宽松：磁盘 90/95、内存 90/97、温度 85/95

开发机磁盘 80% 是常态，用 NAS 的标准会天天告警。温度阈值也放宽到 85/95——开发机满载编译是正常工况。

不检测外设：开发机插拔 U 盘是日常，没有诊断价值。

### `ai` — AI 推理设备

> Jetson / RK3588 / 昇腾等 AI 盒子：算力与内存是重点

| 分类 | 权重 |
|---|---:|
| 算力 | **26** |
| 存储 | 24 |
| 系统与硬件 | 16 |
| 网络 | 14 |
| 安全 | 10 |
| 服务与端口 | 10 |

阈值：磁盘 85/92、内存 85/95、温度 75/85（**最严**）

温度阈值最严，因为这类设备通常是长时间满载推理，且散热空间小。芯片自适应阈值会进一步覆盖这里——RK3588 走 70/82，Jetson 走 75/88。

**只有这个场景，缺加速器才是 FAIL。** 其他场景下 `ai.hardware` 无硬件时是 SKIP。

## 3. 阈值总表

| 阈值键 | `nas` | `verify` | `dev` | `ai` | 用在哪些检查项 |
|---|---:|---:|---:|---:|---|
| `disk_use_warn` | 80 | 85 | 90 | 85 | `storage.capacity` |
| `disk_use_crit` | 90 | 95 | 95 | 92 | `storage.capacity` |
| `mem_use_warn` | 85 | 90 | 90 | 85 | `system.memory_pressure` |
| `mem_use_crit` | 95 | 97 | 97 | 95 | `system.memory_pressure` |
| `inode_use_warn` | 90 | 90 | 90 | 90 | `storage.inode` |
| `swap_use_warn` | 50 | 50 | 50 | 50 | `system.swap_pressure` |
| `temp_warn` | 75 | 80 | 85 | 75 | `system.thermal`（通用芯片） |
| `temp_crit` | 88 | 92 | 95 | 85 | `system.thermal`（通用芯片） |
| `link_speed_min` | 1000 | 1000 | 1000 | 1000 | 速率比较基准 |
| `load_per_core_warn` | 1.5 | 1.5 | 1.5 | 1.5 | `system.load_average` |

有几点需要说明：

- **温度阈值不是所有芯片都用这张表。** RK3588 / Jetson / 昇腾 / 树莓派走各自的硬编码区间，见 [CHECKS.md](CHECKS.md#systemthermal--温度)。
- **硬盘温度（`storage.smart_temperature`）不读这张表。** 它是 50/60 硬编码——机械盘的工作温度区间与 SoC 完全不同，不能共用一套阈值。
- `link_speed_min` 目前只作为基准值存在，`network.link_speed` 内部用的是 100 / 1000 两个分档。

## 4. 怎么选

| 你的机器是 | 用 | 理由 |
|---|---|---|
| 群晖 / 威联通 / 自建文件服务器 | `nas`（默认） | 存储与可用性优先 |
| 正在买二手 NAS，要验收 | `verify` | 安全与损耗优先，阈值放宽避免误报 |
| 软路由 / PVE 宿主 / 常开的开发机 | `dev` | 负载与网络优先，容忍高占用 |
| Jetson / RK3588 / 昇腾盒子 | `ai` | 算力参与评分，缺加速器算严重 |
| 说不清 | `nas` | 默认值对大多数场景是合理的 |

```bash
nastool                       # nas
nastool -p verify             # 二手验机
nastool -p dev -o all         # 开发机，出三份报告
nastool -p ai -v              # AI 设备，显示全部项与证据
```

## 5. 追加分类：`--enable`

```bash
nastool --enable ai           # nas 场景下附加 AI 检测
```

追加的分类若原本权重为 0 或不存在，会拿到**保底权重 8**。这意味着它会真实影响总分，不只是展示。

这个设计是有意为之：如果你主动要求检测 AI，说明你在意它，那它就该参与评分。

注意 `--enable` 与 `--profile` 的差别：

| | 作用 |
|---|---|
| `--profile ai` | 换成 AI 场景：算力占 26 分，温度阈值最严，缺加速器算 FAIL |
| `--enable ai` | 在现有场景上附加 AI 分类：算力占 8 分，其余阈值不变，缺加速器不算 FAIL |

---

## 6. 与 `--only` 的相互作用

`--only` 是**显式指定**，会**完全绕过场景的分类过滤**：

```bash
nastool --only usb.*       # 即使 nas 场景，也只看 usb
nastool -p verify --only storage.smart_*   # 只看 SMART 相关的几项
```

此时 `profile.active` 不再用于筛选，但**权重和阈值仍然生效**。也就是说：

```bash
nastool --only usb.*        # 场景 nas：外设权重 6
nastool -p dev --only usb.* # 场景 dev：外设不在 active，但 --only 强制跑，权重 0 → 得分但不进总分
```

后者会显示外设得分，但因为 `dev` 场景里没有外设权重，它不进总分。这是符合预期的：你指定要看，那就给你看，但不改变这个场景的价值排序。

## 7. 相关代码

| 文件 | 内容 |
|---|---|
| `nastool/profiles.py` | 四个 `Profile` 定义、`_BASE_THRESHOLDS`、`with_categories()` |
| `nastool/engine.py` | 按 `profile.active` 过滤（`--only` 时跳过过滤） |
| `nastool/scoring.py` | 按 `profile.weight()` 加权 |
| `nastool/checks/system.py` | `thermal` 使用 `ctx.threshold()` / `ctx.thermal_limits()` |

新增场景只需在 `PROFILES` 里加一条 `Profile`，其余代码全部自动适配。
