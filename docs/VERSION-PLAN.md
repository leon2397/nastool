# 版本计划

> **这是排期的唯一权威来源。** 技术债在 [memo/debt.md](memo/debt.md)，未决问题在
> [memo/open-questions.md](memo/open-questions.md)，检测项缺口在
> [CHECKS-ROADMAP.md](CHECKS-ROADMAP.md)——但**"什么时候做"只在这里写**。
>
> `python tools/selfcheck.py` 会检查：技术债与未决问题是否都有归属，没有就算漏排期。

**版本号表示顺序，不表示日期承诺。** 什么时候发取决于做得多快，不取决于日历。

## 版本策略

| 阶段 | 语义 |
|---|---|
| **0.x** | minor 内**允许破坏性变更**（删除 CLI 参数、改 JSON 字段），但必须在 `CHANGELOG.md` 写迁移方式 |
| **1.0 起** | 语义化版本：minor 不破坏，patch 只修 bug |
| **报告格式** | `REPORT_VERSION` **独立于**产品版本。字段增删改必须升它，与产品版本无关 |

每个版本固定五步，顺序不变：

```
定范围（本文）→ 实现 → 文档同步 → selfcheck + pytest → 发版
```

**一个版本一个主题，不并行。** 主题分散会让人怀疑每一项都做不透，而做透一件比做半件
三件有价值得多。

## 当前焦点：0.4.0

**下一步具体做这一件**：DEBT-001 多源数据融合与一致性验证。

理由：它是所有"结论可信"类工作的地基。没有多源数据，"融合""置信度""一致性"都无从谈起；
而它一旦落地，DEBT-009（置信度参与判定）才有真实数据支撑，不用继续用拍脑袋的静态值。

---

## 0.4.0 —— 让结论更可信

**目标**：同一个事实有多个来源时，报告能告诉你信哪个，而不是随便挑一个。

**为什么是现在**：目前是"取第一个读到的来源"。在 ARM 板子上，hwmon 温度（SoC 某一点）与
thermal_zone 温度（整机）能差 15°C，取哪个直接决定告警与否，用户无从判断。

| 项 | 来源 | 说明 |
|---|---|---|
| 多源采集 + 一致性验证 | [DEBT-001](memo/debt.md#debt-001-多源数据只有回退没有融合) | 采集层保留全部来源，判定层比对；差 ≤ 阈值取均值，差 > 阈值报"读数存疑"并列出两个来源 |
| 置信度参与判定 | [DEBT-009](memo/debt.md#debt-009-置信度只是展示值不参与打分) | 置信度 < 0.5 的判定不计入分母（等同 UNKNOWN 处理），不再只是展示值 |

**破坏性变更预告**

- `score` 的计算会变：低置信项不再拉低分类分。**已有分数的历史不可直接比较**——
  历史库记录的分数与新口径不同，对比时会失真，需要在对比结果里提示口径变更
- `Evidence` 可能新增表示"来源冲突"的字段，`report_version` 升 4.0

**验收标准**

- 同一台机器跑两次，多源一致的项结论相同（[底线三：结论可复现](../README.md)）
- 人为制造一个两源冲突的 fixture，报告出现"存疑"且两个来源都可见
- 置信度 < 0.5 的项不进分母，且在报告里标出原因
- 六条不变式测试仍全绿（[DEVELOPMENT.md](DEVELOPMENT.md#6-测试)）

**不包含**：不引入第三方数据源包（[ADR-0006](adr/0006-zero-dependency.md)）；
不做 AI 框架逐个点名（见 [CHECKS-ROADMAP.md](CHECKS-ROADMAP.md) 的取舍说明）。

## 0.5.0 —— 让结论可执行

**目标**：从"体检报告"变成"照着做的清单"。

**为什么是现在**：0.4.0 之后结论已经可信，但一个可信的"20 项告警"仍然要用户自己判断
先做哪个。而这几件事成本都不高，是把工具从"诊断"推向"可用"的性价比最高的一批。

| 项 | 来源 | 说明 |
|---|---|---|
| 行动计划 `action_plan` | [DEBT-002](memo/debt.md#debt-002-建议是单条的没有行动计划) | 每条 WARN/FAIL 带 `priority`（0–3）与 `fix_risk`（低/中/高），报告按优先级生成"建议做什么" |
| 系统盘空间检查 | [DEBT-007](memo/debt.md#debt-007-没有系统盘空间检查) | 查 `/`、`/var`（Windows 查 `C:`）。**NAS 上最常见的故障之一**，目前完全没覆盖 |
| 自检命令 `--self-test` | [DEBT-011](memo/debt.md#debt-011-没有自检命令) | 查 Python 版本、必需命令、权限、各采集器能否返回非空，输出"哪一环断了"。不评分、不产生报告 |
| 历史库自动清理 | [DEBT-005](memo/debt.md#debt-005-历史库不会自动清理) | `save()` 时按条数/体积自动裁剪，避免长期部署撑爆小分区 |
| 历史库默认位置 | [Q-008](memo/open-questions.md#q-008-历史库默认放哪) | 与自动清理一起定：默认保持 `~/.nastool/`，文档写清"建议放数据盘"，并支持环境变量覆盖 |
| 分类一致性运行时校验 | [DEBT-006](memo/debt.md#debt-006-分类一致性没有运行时校验) | 加了分类忘了改 profile 会**静默不检测**，导入时就要报错 |
| `tags` 变成真能力 | [DEBT-008](memo/debt.md#debt-008-tags-是死字段) | 实现 `--tag` 筛选，或删掉字段。二选一，不能继续留死字段 |
| Windows 单项超时 | [DEBT-004](memo/debt.md#debt-004-单项超时只在-posix-生效) | 现在 Windows 上某项卡住会挂住整次运行 |
| 上报失败可选致命 | [Q-002](memo/open-questions.md#q-002-上报失败要不要影响退出码) | 新增 `--push-required`，默认行为不变 |
| 分数不可比的表述 | [Q-006](memo/open-questions.md#q-006-跨设备的分数可以比较吗) | 明确写"分数只在同一台机器的时间纵向上有意义"，报告与文档同步 |
| `--only` 后分数的措辞 | [Q-007](memo/open-questions.md#q-007---only-过滤后总分还有意义吗) | 过滤后的报告标注"不代表整机健康度" |

**破坏性变更预告**

- `report_version` 升 4.1（`checks[].priority` / `fix_risk` 与新的 `action_plan` 段为新增字段）
- 行动计划的措辞会出现在报告里，终端输出长度增加

**验收标准**

- 20 项告警的报告能给出排序后的建议清单，每条有优先级与风险标注
- `--self-test` 能在缺 `smartctl` 的环境下指出"SMART 数据不可读"这一环
- 故意加一个新分类但不配权重 → 导入即报错（不是静默不检测）
- Windows 上某项阻塞 → 60 秒后该项标 `UNKNOWN` 而非挂住

**不包含**：不做自动修复（[ADR-0007](adr/0007-no-fix-engine.md)）；不生成可执行的修复脚本
（[Q-001](memo/open-questions.md#q-001-要不要生成修复脚本只生成不执行) 倾向不做）。

## 0.6.0 —— 看得更清

**目标**：从"看得到表面"到"看得到真实状态"。

**为什么是现在**：服务检测目前只看"端口在不在听"，这是与通用 NAS 工具最实质的差距——
进程活着、端口在听、但协议握手失败（SMB 版本协商不过、证书过期导致 Web UI 打不开），
报告会显示一切正常，而用户此刻连不上。

| 项 | 来源 | 说明 |
|---|---|---|
| 服务协议级探测 | [DEBT-003](memo/debt.md#debt-003-服务只探端口不验协议) | SMB 协商、NFS 导出查询、HTTP 头、SSH banner。**严格只读**，不认证不写 |
| Windows 深度支持 | [DEBT-010](memo/debt.md#debt-010-windows-支持深度不足) | `Get-PhysicalDisk`/`Get-Disk`（RAID 与健康）、`Get-NetAdapter`（链路）、`Get-SmbShare`。决策见 [Q-010](memo/open-questions.md#q-010-windows-支持做到什么程度) |
| 踩坑守门测试 | [DEBT-013](memo/debt.md#debt-013-一半的坑没有守门测试) | 把 PowerShell/命令输出做成固定 fixture，让 6 条无守门的坑可测 |
| 前身缺口补齐 | [CHECKS-ROADMAP.md](CHECKS-ROADMAP.md) | 登录失败次数 / 系统日志错误、NAS 平台专属项（DSM/QTS 版本判定、UPS、备份任务） |
| 仓库瘦身 | [DEBT-012](memo/debt.md#debt-012-reference-目录不进构建但占体积) | `reference/` 移出主仓或标 vendored |

**破坏性变更预告**

- 新增若干检测项 → `report_version` 升 4.2
- **Windows 上的检测项集合会变大** → 覆盖率数字、分类得分都会变，历史对比会看到"新增项"
- 若接入 NAS 平台专属项，检测项 id 会增加（**已有 id 不变**，[STANDARDS.md](STANDARDS.md#8-兼容性承诺-硬)）

**验收标准**

- 一个 SMB 服务进程存在但共享未配置时，报告能区分"端口在"与"共享可用"
- Windows 上新增项有真机验证记录
- 6 条无守门的踩坑各有对应测试，`gotchas.md` 的"守门"列全部转为 ✅
- [CHECKS-ROADMAP.md](CHECKS-ROADMAP.md) 的缺口表与 `--list-checks` 输出对得上

**不包含**：不补 AI 框架清单（无边界、无业务意义）；不做 USB 权限/供电检测
（NAS 场景价值最低）。

## 1.0.0 —— 承诺稳定

**目标**：从"好用的工具"变成"可以被依赖的契约"。

1.0 不是"功能更多"，是**承诺**：报告格式在 1.x 内只加字段不改不改；检测项 id 永不改名；
退出码语义不变；CLI 参数只加不删。

| 项 | 来源 | 说明 |
|---|---|---|
| 报告格式兼容承诺 | [Q-003](memo/open-questions.md#q-003-report_version-30-稳定后要不要承诺向后兼容) | 冻结 `3.x`/`4.x` 只加字段，破坏性变更留给下一个 major |
| 插件机制决策 | [Q-004](memo/open-questions.md#q-004-要不要开放第三方检测项插件) | 做或不做都要在 1.0 前定。倾向**不做**（`CheckContext` 还会变） |
| 国际化决策 | [Q-009](memo/open-questions.md#q-009-输出要不要国际化) | 做或不做都要在 1.0 前定。契约字段已是英文，改造点在展示层 |
| 1.0 门槛校验 | — | 见下 |

**1.0 的门槛清单**（全部满足才算 1.0）

- [ ] `report_version` 冻结，且有明确的兼容策略写进 [OUTPUT.md](OUTPUT.md)
- [ ] 至少在 **3 台真实设备**上验证过（含一台 NAS、一台非 NAS 的 Linux、一台 Windows）
- [ ] `selfcheck` 10 项全绿并纳入发版流程
- [ ] 文档无断链、无过期数字（由 `selfcheck` 保证）
- [ ] [memo/debt.md](memo/debt.md) 里没有 P0 级未修项
- [ ] [memo/open-questions.md](memo/open-questions.md) 里没有"影响 1.0"的开放问题
- [ ] 从 `de67165`（0.2.0）到 1.0 的完整变更可在 `CHANGELOG.md` 读通

**破坏性变更预告**：无。1.0 本身不引入破坏性变更，它**禁止**未来的破坏性变更。

## 明确不做的决定

记在这里，是为了**不再反复讨论**。要改变这些决定，得走 [ADR](adr/) 流程。

| 事项 | 结论 | 理由 | 出处 |
|---|---|---|---|
| 自动修复 | **不做** | 体检工具变成治疗工具，风险从工具转移到用户判断力 | [ADR-0007](adr/0007-no-fix-engine.md) |
| 生成可执行修复脚本 | **倾向不做** | 完整脚本会诱导用户一把梭执行；最多给 diff 式建议（原行/建议行） | [Q-001](memo/open-questions.md#q-001-要不要生成修复脚本只生成不执行) |
| 多机批量体检（远程执行） | **不做** | 一旦支持远程就要处理凭据、SSH 密钥、失败重试、并发限流——那是另一个产品 | [Q-005](memo/open-questions.md#q-005-要不要支持多机批量体检) |
| 引入第三方运行时依赖 | **不做** | 检测工具会被拷到没有 pip、没有外网的机器上跑 | [ADR-0006](adr/0006-zero-dependency.md) |
| AI 框架逐个点名 | **不做** | 框架清单没有边界，与设备健康无关；改为验"能不能真跑起来推理" | [CHECKS-ROADMAP.md](CHECKS-ROADMAP.md) |

## 依赖关系

```
0.4.0  多源融合 ──→ 置信度参与判定
        （后者依赖前者，没有真数据支撑就是拍脑袋的权重）

0.4.0  ──→ 0.5.0   行动计划的优先级需要可信度支撑
                 不准的结论不该被排进"最优先做"

0.5.0  ──→ 0.6.0   协议探测产出的问题需要 action_plan 才能被行动
                 Windows 深度支持需要 0.5.0 的超时机制兜底

0.6.0  ──→ 1.0.0   1.0 前必须冻结所有对外契约
```

**跨版本不能拆的**：DEBT-001 与 DEBT-009 必须在同一个版本（0.4.0）完成，拆开会让中间版本
既付出了融合的成本，又拿不到融合的收益。

## 排期外的常驻工作

每个版本都要做，不单独排期：

- `selfcheck` 全绿 + `pytest` 全绿
- 文档同步（[STANDARDS.md](STANDARDS.md#10-文档同步-硬-自动) 的对照表）
- `CHANGELOG.md` 记录，破坏性变更写迁移方式
- [memo/journal.md](memo/journal.md) 留一笔；踩坑与技术债随手登记
- 版本号三处同步（`VERSION` / `__init__.py` / `pyproject.toml`）

## 变更这份计划

- 范围调整 → 直接改本文，并在 [memo/journal.md](memo/journal.md) 记一笔
- 改变一个"明确不做"的决定 → 走 [ADR](adr/) 流程，并更新本文
