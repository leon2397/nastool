# ADR-0011：覆盖度的字段名用 `trustworthy`，不与分类的 `usable` 混用

- **状态**：已采纳（v0.4.0 发版前修订）
- **日期**：2026-10-28
- **相关**：[ADR-0009](0009-confidence-participates-in-scoring.md)、[DEBT-009](../memo/debt.md)

> **本条取代 ADR-0009 中关于字段命名与含义的一句话表述**（「顺带新增 `usable` 与
> `usable_percent`：真正对分数有贡献的项数与占比」）。ADR-0009 的其余决策
> ——阈值 `<= 0.5`、按 PASS / FAIL 非对称处理——**继续有效**。

---

## 背景

实现 DEBT-009 时，覆盖度侧和分类侧各加了一个叫 `usable` 的字段。看上去对称，
实际含义不同：

| | `Coverage.usable` | `CategoryScore.usable` |
|---|---|---|
| 分子来源 | `judged − 全部低置信项` | `judged − 被剔除的项` |
| 低置信 PASS | 剔除 | 剔除 |
| 低置信 FAIL | **也剔除** | **保留**（照样扣分、照样触发封顶） |
| 实际含义 | 有多少项的**结论可信** | 有多少项**参与了打分** |

差异来自 ADR-0009 的非对称规则：低置信的 FAIL 不可信，但它**确实计入了分数**
（宁可误报不可漏报）。于是 `coverage.low_confidence` 统计的是**全部**低置信项，
而 `CategoryScore.low_confidence` 统计的是**被剔除的**项。

更糟的是，`Coverage.usable` 的 docstring 写的是「真正对分数有贡献的项数」——
**这句话是错的**。低置信 FAIL 是有贡献的，却被算进了「不可信」里。

## 问题

1. **同一个 JSON 文档里两个 `usable` 含义不同。** 消费方看到
   `coverage.usable` 很容易理解成「参与打分的项数」，但它不是。
2. **docstring 在说谎。** 字段的说明与实际计算不符，违反项目的「文档必须与代码一致」。
3. **报告分母对不上账的风险。** 分类侧的分母必须与实际打分分母严格一致，
   否则终端上显示的 `12/15` 和分数对不上。覆盖度侧不需要满足这个约束，
   两个约束不同，字段就不该同名。

## 决策

覆盖度侧改名，分类侧不动：

| | 旧名 | 新名 | 含义 |
|---|---|---|---|
| 覆盖度 | `coverage.usable` | **`coverage.trustworthy`** | 有可信结论的项数 |
| 覆盖度 | `coverage.usable_percent` | **`coverage.trustworthy_percent`** | 可信结论的占比 |
| 分类 | `categories[].usable` | 不变 | 真正参与打分的项数 |

命名规则：**衡量「结论有多可信」用 `trustworthy`，衡量「有多少项参与了计算」用 `usable`。**

## 后果

### 好处

- 报告契约里不再有「同名不同义」的字段
- `Coverage.usable` 那句错误的 docstring 变成准确的描述
- 打分算法、盲区口径、封顶阈值**一律不变**——只改名字和说明，不改计算

### 代价（必须诚实写出）

- `report_version` 4.0 的字段名与最初设计不同。虽然 4.0 尚未发布、成本为零，
  但**这份 ADR 本身就是变更的证据**：如果当初没多看一眼，
  这个坑会带着「同名不同义」进入第一个发布版本。
- 已经写了「覆盖度新增 usable / usable_percent」的文档要全部改一遍
  （CHANGELOG / OUTPUT / VERSION-PLAN / ADR-0009 / memo 台账）。

### 缓解

- 回归测试新增 `test_coverage_trustworthy_differs_from_category_usable`，
  用低置信 FAIL 做样本，把两个口径的差异钉死。
- `tools/smoke.py` 里也加了同样的断言，CI 每次发版前都会跑。

## 考虑过但否决的方案

### 方案 A：让覆盖度也只统计被剔除的项

把 `Coverage.low_confidence` 改成只数低置信 PASS，这样两个 `usable` 就统一了。

**否决理由**：`blind_percent` 的设计意图（见 `model.py` 的 docstring）是
「如果一半的检查结论都存在争议，那这份报告就不该给出『状态良好』的评价」。
改口径后，结论有争议的 FAIL 不再计入盲区，这条意图就被削弱了。
而且盲区占比会变，74 / 84 两道封顶阈值要重新校准——那是版本计划里钉死的数字，
不该为了让字段名好看来而改动它们。

### 方案 B：把分类侧也改成 `trustworthy`

**否决理由**：分类侧的 `usable` 就是打分分母，报告里显示的 `12/15` 必须等于
实际参与计算的那 15 项里的 12 项。改名字不解决问题——问题在同名，不在分类侧。

### 方案 C：保留同名，靠文档说明区分

**否决理由**：JSON 是给机器消费的。字段名本身就是契约，文档说明救不了一个
语义错误的字段名。而且 docstring 已经在说谎——这是「文档会漂移」的经典案例。

### 方案 D：改回 ADR-0009 的原名，把这条 ADR 删掉

**否决理由**：那等于明知字段语义不对还要发布。ADR 的存在意义就是
「把踩过的坑记下来，不让它再坑一次」。
