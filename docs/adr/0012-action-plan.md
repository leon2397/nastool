# ADR-0012：行动计划由检测项自己声明紧急度，报告只负责排序

- **状态**：已采纳
- **日期**：2026-11-01
- **相关**：[DEBT-002](../memo/debt.md#debt-002-建议是单条的没有行动计划)、[ADR-0007](0007-no-fix-engine.md)、[ADR-0002](0002-collect-does-not-judge.md)

## 背景

到 0.4.0 为止，报告已经能回答「这台机器有什么问题」并且「这个问题有多可信」。
但它**回答不了「我今晚只有半小时，先修哪个」**。

一份正常的 NAS 体检会产出十几到二十条 WARN/FAIL。它们此前在报告里按
「分类 → 严重度」排列，而这个顺序对用户基本无意义：

- `storage.smart_health` FAIL（硬盘有坏道）和 `security.telnet_port` FAIL（Telnet 开着）
  在同一个严重度上，但前者可能导致数据全丢，后者只是安全卫生问题
- 反过来，同样是「修它」，关掉 Telnet 是改一行配置、换硬盘要拆机器——风险差一个量级
- 用户实际做的是「排除法」：读二十条建议，自己在脑子里排优先级。**这件事工具比人更有条件做**

前身的 `action_plan` 有 `priority` 与 `risk` 两个维度（见 [DESIGN-NOTES](../DESIGN-NOTES.md)），
但当时没有「结论可信」这个前提，优先级排得再准也可能是基于错数据的排序。

## 决策

**在检测项上声明紧急度，报告层只做排序。**

1. `CheckResult` 新增两个字段，语义固定：

   | 字段 | 取值 | 回答的问题 |
   |---|---|---|
   | `priority` | 0–3 | **不修会怎样**（后果的严重程度） |
   | `fix_risk` | 低 / 中 / 高 | **修的时候可能弄坏什么**（动作本身的风险） |

   ```
   3 立即处理   数据丢失 / 安全暴露 / 设备随时可能挂
   2 尽快处理   服务不可用或即将不可用
   1 计划处理   配置不合理、性能受损、版本落后
   0 可选优化   有则更好，不做也不影响使用
   ```

2. **由检测项自己声明**，写在 `@check(...)` 装饰器上，而不是在报告层按
   `(category, status)` 查表推导。理由：**判定项比评分器更清楚这件事多急**。
   只有 `storage.capacity` 自己知道「90% 是今晚就要清」而「80% 可以明天再看」——
   这种同项不同状况的差异，任何集中式映射表都表达不了。

3. **同一项可以按状况返回不同优先级**。`R(...)` 接受 `priority` / `fix_risk` 覆盖，
   典型用例如下（三处已落地）：

   | 检测项 | 状况 | priority |
   |---|---|---|
   | `storage.capacity` | 已用 ≥ 95% | 3 |
   | `storage.capacity` | 已用 ≥ 85% | 2 |
   | `system.thermal` | 超过安全线 | 3 |
   | `services.risky_ports`（Docker 2375 明文） | 等同于把 root 交出去 | 3（默认 2） |

4. **`action_plan` 是派生而非存储**：`Report.action_plan()` 从 `checks` 现算，
   不落库、不缓存。存一份就必然与 `checks` 漂移，而这个项目已经吃过
   「同一个数字在文档里有三种说法」的亏。

5. **排序三层，每层都可解释**：

   ```
   ① priority 降序        —— 主维度：不修的后果
   ② 状态严重度（FAIL 先） —— 同优先级下，已坏优先于将坏
   ③ fix_risk 升序        —— 同样紧急时，先做不容易弄坏的
   ④ id 兜底              —— 保证两次运行顺序一致（结论可复现）
   ```

   第 ③ 层是这套设计里最不显然的一层，也是它区别于「按严重度排」的地方：
   它服务的正是「我今晚只有半小时」这个真实处境。

6. **只有 WARN / FAIL 进清单**。PASS 不需要行动；而 UNKNOWN 需要的不是
   「行动」而是「先让它能测」——那是 `--self-test` 的职责（DEBT-011）。
   把「请安装 smartctl」混进行动清单，会让用户拿着一份修复清单去修一台其实完好的机器。

## 后果

### 好处

- 报告从「问题清单」变成「排好序的待办」
- 优先级与风险是**数据**而非文案：JSON 消费方可以自己重排、过滤、接进工单系统。
  写死在 `suggestion` 文本里的「建议尽快处理」机器读不懂
- 新增检测项时**必须**回答「这件事多急、修它多险」，这是一次强制的自我审视。
  此前写 `suggestion` 是自由发挥，现在有了可比较的标尺

### 代价（诚实写出）

1. **55 项标注是人工判断，没有客观依据可校验。** selfcheck 能查
   「有没有标」，查不了「标得对不对」。判断错误的代价是排序失真，
   而排序失真不会报错——它只会让用户先修错东西。缓解：把判断写进
   [CHECKS.md](../CHECKS.md) 的说明，让标注可被 review，而不是藏在代码里
2. **默认值会掩盖「忘了想」**。`priority` 默认 1、`fix_risk` 默认 中——
   都忘标时报告仍能出，但那份排序是假的。缓解：默认值取保守值（不是 0、不是 低），
   并在样式上要求新项显式声明
3. **报告变长**：终端多出一段「建议做什么」。缓解：清单只列 WARN/FAIL 且每条一行，
   `--quiet` 场景不额外输出
4. **契约新增字段**，`report_version` 4.0 → 4.1。缓解：纯新增，旧消费方忽略即可

### 缓解

- 动态覆盖必须写注释说明「为什么这个状况更急」，让下一个人能判断是否仍然成立
- 归一化放在 `CheckResult.__post_init__`，任何构造路径都拿到合法值，
  报告器不必到处判空（避免「某一处忘了判空就崩」）

## 考虑过但否决的方案

**① 在报告层用 `(category, status)` 查表推导优先级**
否决。表是死的，状况是活的。查表能表达「存储比网络重要」，
表达不了「同样是存储，95% 和 85% 差一级」。

**② 让 `priority` 影响分数（等同权重的第二维度）**
否决。分数答「这台机器多健康」，`priority` 答「先修哪个」，两个问题混在一起，
用户会看到「硬盘要坏」把总分拉到 30，却不知道为什么。——这是
[ADR-0009 的非对称教训](0009-confidence-participates-in-scoring.md)的同一类错误：
把两个不同的问题塞进一个数字。**优先级只影响排序，不影响分数。**

**③ 给 `action_plan` 加「预计耗时」「影响面」等更多维度**
否决（当前）。维度越多，标注越随意，用户越不看。
`priority + fix_risk` 两个维度已经能覆盖「先做什么、敢不敢动」，
其它信息放 `suggestion` 文本里更合适。真需要时再开 ADR，而不是现在留空字段。

**④ 顺势做修复引擎**（按 action_plan 自动执行）
明确不做，见 [ADR-0007](0007-no-fix-engine.md)。清单是给人看的，
不是给脚本吃的——一旦能自动执行，「误判就变成误操作」，风险等级完全不同。

## 教训

1. **能从数据派生出来的东西，不要存第二份。** `action_plan` 存进报告就是一个
   必然漂移的副本；现算的成本是几毫秒，收益是永不不一致。
2. **默认值的方向要对**：`priority` 默认 1（不是 0）、`fix_risk` 默认 中（不是 低）。
   忘标时应该「保守」，而不是「乐观」——乐观的默认值会把风险静默抹平。
3. **排序规则要能被讲出来**。三层排序每层都有一句人话解释（见上），
   否则三个月后没人敢改它——改一个 `key=` 里元组的顺序，输出会全变，
   而没有测试能告诉你「变好还是变坏」。
