# ADR-0009：置信度参与判定，且低置信项按 PASS / FAIL 非对称处理

- **状态**：已采纳
- **日期**：2026-10-28
- **相关**：DEBT-009、[ADR-0004](0004-two-cap-rules.md)、[ADR-0008](0008-multi-source-fusion.md)

## 背景

DEBT-009 记录的原状：

> 每项有 `confidence`，报告汇总一个加权平均。但 `_category_score()` 不乘它，
> 低置信度的 PASS 与高置信度的 PASS 得分完全相同。

也就是说，置信度**只是个展示值**。一个靠猜得出 PASS 的项，和一个从内核直接读到的
PASS，对分数的贡献一模一样。报告会写「置信度 0.45」，但这个数字对结论毫无影响。

DEBT-009 原本给的修法是：

> 置信度 < 0.5 的判定不计入分母（等同 UNKNOWN 处理），只做展示。

这条修法有两个问题，实现前必须解决。

## 问题一：对称处理会漏报

如果对**所有**低置信项一视同仁地剔除分母，那么一个低置信的 **FAIL**
（置信度 0.4）也会被从分数里抹掉。

后果是具体的：

- 该项不再拉低分类得分
- **不再触发封顶 59**——封顶逻辑看的是「有没有 FAIL」
- 报告会说这台设备健康，而实际上有一个「疑似严重问题」被忽略了

这与产品原则「假告警比漏报更糟」**直接冲突**。漏报会让用户不做任何处理，
误报顶多让用户多看一眼。

## 问题二：阈值卡在边界上

DEBT-009 写的是「置信度 **<** 0.5」。

但 [ADR-0008](0008-multi-source-fusion.md) 定的衰减下限是 0.5——多源读数冲突时
置信度**恰好落在 0.5**（`fusion.py` 的 `_confidence()` 在超出容差时衰减到 0.5）。

用严格小于 `< 0.5`，那么**唯一能产出低置信判定的路径，恰好整个被漏掉**。
这不是理论风险，是当前代码的实际行为。

## 决策

### 一、阈值用 `<=`，覆盖边界

```python
MIN_CONFIDENCE_FOR_SCORING = 0.5
# 判定：confidence <= 0.5
```

边界值本身也要被处理——它不是「刚好合格」，它正是「刚好不可信」的那一类。

### 二、按状态非对称处理

| 判定 | 置信度 | 计入分数分母 | 计入盲区 |
|---|---|---|---|
| PASS | > 0.5 | 是 | 否 |
| PASS | ≤ 0.5 | **否** | **是** |
| WARN / FAIL | 任意 | **是** | 否 |
| UNKNOWN / SKIP | — | 否 | `unknown` 计入 |

规则落在一处：`CheckResult.counts_toward_score`。评分层、三个报告器都用它，
避免出现「终端说没计分、JSON 算进去了」这类不一致
（这正是 [ADR-0003](0003-registry-over-hardcoded-wiring.md) 解决的「多处硬编码导致
说法不一」那类问题的再次出现）。

### 三、低置信的 FAIL 照样封顶

封顶逻辑（[ADR-0004](0004-two-cap-rules.md)）用**全部** FAIL 项，不筛置信度。

理由与上面一致：可疑的严重问题必须影响结论。「读不准」不等于「没问题」。

### 四、低置信项计入盲区，但不等于 UNKNOWN

覆盖度新增 `low_confidence` 计数，与 `unknown` **分开**：

| | 含义 | 典型成因 |
|---|---|---|
| `unknown` | **没测到** | 权限不足、工具缺失、读不到接口 |
| `low_confidence` | **测到了但不可信** | 多来源读数互相矛盾 |

两者都计入 `blind_percent`（结论确实有限），但报告要分开显示——否则用户会以为
所有不确定都是「工具没装好」，从而给出错误判断。

顺带新增 `usable` 与 `usable_percent`：真正对分数有贡献的项数与占比。

> **本文的字段命名已被 [ADR-0011](0011-coverage-field-naming.md) 取代**：
> 覆盖度侧改名为 `trustworthy` / `trustworthy_percent`。
> 本文其余决策（阈值 `<= 0.5`、按 PASS / FAIL 非对称处理）**继续有效**。

### 五、口径变更时不给差值

置信度参与判定改变了 `score` 的计算方式，因此 `report_version` 从 3.0 升到 4.0。

历史库里的旧分数与新分数**不可直接相减**——差值里一半来自设备变化、
一半来自口径变化。`diff.py` 会比对两次报告的 `report_version`，
不一致时：

- `score_comparable = False`
- `score_delta()` 返回 `None`（而不是误导性的差值）
- 报告里显示「口径不同，差值不可比」并给出说明

## 被否决的方案

### 「乘权重」——置信度打折计入

DEBT-009 自己就警告过：「不要简单地乘权重——那会让『读不到』变成『少扣点分』，
反而更糟」。

具体到实现：低置信的 FAIL 打折后扣分变少，一块疑似坏了的盘扣 2 分而不是 5 分，
分数封顶仍会触发（这部分没问题），但分类得分会被抬高。效果与对称剔除类似，
问题一样。**否决。**

### 「所有低置信项一视同仁」——对称处理

见「问题一」。会漏报。**否决。**

### 「阈值用 `< 0.5`」

见「问题二」。边界正好卡在唯一需要提示的那一类上。**否决。**

### 「只降权不剔除」——按置信度给分类分加权

与「乘权重」同源，同一个问题。**否决。**

## 后果

- **平时不改变分数**：绝大多数检查项置信度在 0.85–1.00，落在阈值之上。
  这条规则只在「多源数据打架」时起作用——而那正是最需要它的时候。
- **分数口径变了**：`report_version` 4.0，历史对比会提示。
- **报告多了一处解释**：低置信项会标「⚠ 结论存疑」并说明
  「该项未计入分数」，避免用户以为分数算错了。
- **测试**：新增 `tests/test_debt009_confidence.py`（18 项），
  并通过变异测试验证——把实现改成对称处理、阈值改严格小于、
  低置信项不计入盲区、去掉口径检测，四种劣化全部被测试精确捕获。

## 复盘

这条 ADR 的价值不在于「置信度要参与判定」——那是 DEBT-009 早就写好的。

价值在于：**它把一个看起来对称的规则，改成了非对称的**，理由是
「对称看起来公平，但在这个产品里，漏报的代价远高于误报」。

凡是「好结果与坏结果处理方式不同」的规则，都应该先问一句：
**把坏消息排除掉，是让报告更好看，还是让报告更危险？**
