# 0001. 「不可判定」是一等状态，不是失败

- 状态：生效
- 日期：2026-10-28（0.3.0）
- 影响：数据契约、评分、报告、所有检查项的实现方式

## 背景

体检类工具最常见的可信度问题不是「测不准」，而是**把「没测到」伪装成一个结论**。

0.2.0 只有布尔式的结果：要么通过，要么有问题。于是「读不到 SMART」必须二选一：

| 选择 | 后果 |
|---|---|
| 当成通过 | 掩盖真实风险。用户看到「SMART 正常」，其实根本没读到 |
| 当成失败 | 制造假故障。非 root 用户跑一次就报「硬盘要坏」 |

两条路都是错的。而真实世界里「读不到」的比例很高：非 root、容器内、硬件 RAID 卡后面、USB 硬盘盒、虚拟机——这些场景下 SMART 全都读不到。

同类工具通常的做法是「读不到就静默跳过」，用户根本不知道哪些项没查。一份 100 分的报告可能只判定了 30% 的适用项。

## 决策

引入第五种状态 `Status.UNKNOWN`，与「通过/告警/严重/不适用」并列。

五态定义：

| 状态 | 含义 | 计分 | 覆盖度分母 |
|---|---|:--:|:--:|
| PASS | 读到了，正常 | 1.0 | 计入 |
| WARN | 读到了，有问题但可用 | 0.5 | 计入 |
| FAIL | 读到了，确认严重 | 0.0 | 计入 |
| **UNKNOWN** | **该查但没查到** | **不参与** | **计入（形成盲区）** |
| SKIP | 不适用 | 不参与 | **不计入** |

关键区分是 UNKNOWN 与 SKIP：

- UNKNOWN **进分母**，因此会拉低覆盖率、形成盲区、触发封顶
- SKIP **不进分母**，因为这台机器本来就没有这个概念

配套的两个机制：

1. `Coverage.blind_percent = unknown / applicable`，并在盲区 ≥30% / ≥50% 时封顶等级（见 [ADR-0004](0004-two-cap-rules.md)）
2. 终端报告会逐条显示 UNKNOWN 的**具体原因**（「缺少依赖：smartctl，本次未检测」），而不是悄悄跳过

## 后果

### 好处

- 「读不到」不再需要伪装。检查项可以坦率地说「我没看到」
- 用户能一眼看出报告的解释力边界：`覆盖 20/20（100%）` 与 `覆盖 8/19（42%）` 是完全不同的两份报告
- 消除了「非 root 跑就报硬盘坏」这类假警报
- 为封顶规则提供了数据基础——没有 UNKNOWN 就无法量化盲区

### 代价

- **必须维护两套「不参与计分」的语义**（UNKNOWN vs SKIP），每个检查项作者都要判断自己遇到的是哪一种。这是本项目最容易写错的地方，`docs/DEVELOPMENT.md` 专门用一节讲这个
- 报告变复杂：多了一个状态符号（`?`）、一行盲区统计、一种封顶原因
- 用户初次看到「C 级但全部通过」会困惑，需要文档解释「这是没查清，不是有问题」

### 缓解

- `docs/CHECKS.md` 逐项写明每种情况对应哪个状态
- `checks/_base.py` 的 docstring 直接给出正确/错误示例
- 测试 `test_unknown_does_not_deduct_category_score` 锁住「UNKNOWN 不扣分」这一条

## 考虑过但否决的方案

**加一个 `confidence=0` 的 PASS**：不新增状态，用置信度表达不确定。

否决理由：置信度是连续值，无法参与「进不进分母」这种离散判定。而且「低置信度的通过」在报告里仍然显示为通过，视觉上和确定的通过无法区分——这就回到了掩盖问题的老路。
