# ADR-0008：多源数据融合放在判定层，温度取最高值而非平均值

- **状态**：已采纳
- **日期**：2026-10-28
- **相关**：DEBT-001、[ADR-0002](0002-collect-does-not-judge.md)、[ADR-0004](0004-two-cap-rules.md)

## 背景

同一个事实在不同系统上可能有多个来源。DEBT-001 记录的具体场景：

某些 ARM 板子的 `/sys/class/hwmon` 只报告 SoC 上某一点的温度，而 `/sys/class/thermal` 报告的是整机热点。两个读数可以差 15°C。旧实现是「hwmon 优先，thermal_zone 兜底」——hwmon 有值就完全不读 thermal_zone。

这会导致：取哪个读数直接决定「是否告警」，而用户从报告里**看不出存在争议**。报告说「60°C 正常」或「45°C 正常」，取决于先读到哪个文件。

前身项目 v7.1.0-beta 有 `DataFusionEngine` 与 `ConsistencyValidator`（见 `reference/legacy/docs/API.md`），但**代码内核已丢失**，只剩 API 文档。前身列了 4 种融合方法（`WEIGHTED_AVERAGE` / `MEDIAN` / `MAJORITY_VOTE` / `TRUSTED_SOURCE`）与三类一致性检查（时间 / 值 / 趋势）。

## 决策

### 一、融合放在判定层，不放采集层

采集层**保留全部来源的原始读数**，判定层做验证与融合。

这不违反 [ADR-0002](0002-collect-does-not-judge.md)（采集层不判断好坏）：「保留两个读数」是**事实的完整性**，不是判断；「差 15°C 算不算矛盾」「该信谁」才是判断。

融合模块 `nastool/fusion.py` **只做数值运算**——它不知道什么叫「温度过高」，只知道「两个值差了 12，超过容差 5」。把结果翻译成 PASS / WARN / FAIL 是 `checks/` 的职责。

### 二、温度用 MAX 融合，不用平均值

这是本决策里最容易被做错的一点。

把 SoC 的 45°C 和热点的 60°C 平均成 52.5°C，看起来「折中」，实际是**低估散热风险**。温度是「取最高才安全」的量——CPU 45°C 说明芯片本身凉，但热点 60°C 说明散热已经跟不上了。平均值把这个信号抹掉了。

同理，容量、错误计数、坏道数这类量也应当取最坏值。所以 `FusionMethod` 里加了 `MAX`，它不是「加权平均的变体」，而是**语义不同**的一种融合。

### 三、一致性验证只在「同一测量点」内进行

不是所有温度读数都互相可比。CPU 45°C 与 GPU 70°C 不是矛盾，是两个不同的测量点。

所以要先做**测量点归一化**：`cpu` / `soc` / `cpu-thermal` / `x86_pkg_temp` → `cpu`；`gpu` / `gpu-thermal` → `gpu`。

归一化错了的代价很大：会把「CPU 45 + GPU 70」误判成矛盾，产生一个**假的告警**。这比漏报更糟——用户会为一个不存在的问题去拆机器。

### 四、矛盾时降置信度，但不隐藏矛盾

两个来源不一致时：

- 判定状态取**最坏**的那个（安全优先）
- 置信度降到 0.5
- 报告里显示「⚠ 结论存疑」并列出**两个来源的具体读数与差值**
- 建议里提示人工核对传感器

绝不「随便采信一个然后当作没问题」。这正是 DEBT-001 说的「随便采信一份」。

### 五、只有两个来源时不判「离群」

两个来源各执一词时，没有第三个参照，无法认定谁是错的。此时只能说「两者不一致」，不能说「hwmon 是离群的」。

`validate()` 因此只在 ≥3 个来源时才输出 `outliers`。

## 后果

**好的**：

- 报告里的温度结论更可靠：数据有争议时明说，而不是给一个看起来确定的数字
- 采集层与判定层职责更清晰：采集只管「读到了什么」，判定管「这说明什么」
- 融合机制可复用到其他多源事实（NVMe 的 `smartctl` vs `nvme-cli`、内存的 `/proc/meminfo` vs `sysinfo`）

**代价**：

- 温度采集要多读一个文件（`/sys/class/thermal`），耗时略增
- 报告里可能出现「读数存在争议」这类用户需要理解的新表述
- 测量点归一化表需要维护——新硬件的传感器命名可能需要加别名

**中性**：

- `REPORT_VERSION` 未变（3.0）。融合不改变 JSON 的结构，只改变部分 `checks[]` 条目的 `summary` / `detail` / `confidence` 值。

## 备选方案

| 方案 | 为什么没选 |
|---|---|
| 采集层直接融合，只留一个值 | 判定层就看不到争议了，等于回到旧问题 |
| 保持互斥兜底，但选「更可信」的来源 | 「可信」需要跨来源比较才能得出，单来源选不出来 |
| 用平均值 | 低估散热风险，语义错误（见上文） |
| 不一致时直接判 UNKNOWN | 温度确实能读出来，只是有争议。判 UNKNOWN 会让「有分歧」和「读不到」混为一谈，且不扣分反而可能掩盖真实的高温 |
| 不一致时判 FAIL | 误报代价高；正确做法是「取最坏值判定 + 标注争议 + 降置信度」 |
