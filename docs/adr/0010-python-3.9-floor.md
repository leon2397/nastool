# ADR-0010：Python 版本下限从 3.8 抬到 3.9

- **状态**：已采纳
- **日期**：2026-10-28
- **相关**：[ADR-0006](0006-zero-dependency.md)、DEBT-016

## 背景

建 CI 时（[DEBT-016](https://github.com/leon2397/nastool/blob/main/docs/memo/debt.md)），
第一轮 CI 跑出来 15 格矩阵里挂了 10 格。逐格定位后发现是两个**独立**的问题：

| 现象 | 失败步骤 | 根因 |
|---|---|---|
| 所有平台的「端到端冒烟」 | 端到端冒烟 | CI 脚本断言了退出码为 0（见下） |
| Python 3.8（所有平台） | 安装依赖 | `pip install -e .` 直接失败 |

第二个是真正的兼容性问题，暴露了一个**落空的承诺**：

```toml
requires-python = ">=3.8"
[build-system]
requires = ["setuptools>=77"]
```

`setuptools` 从 **76.0.0 起要求 Python >= 3.9**（实测 PyPI 元数据），
而 `license-files`（现代打包规范，取代已弃用的 `license = {text = ...}`）
需要 setuptools >= 77。

所以在 Python 3.8 上：`pip install` 装不上 → 声明的「3.8+ 任意机器直接跑」是假的。

## 决策

**把版本下限抬到 3.9**，与现实对齐。

```toml
requires-python = ">=3.9"
```

同步调整：CI 矩阵去掉 3.8（从 15 格变 12 格）、README / CLI / DEVELOPMENT /
STANDARDS / PRODUCT-PLAN / VERSION-PLAN / ADR-0006 共 8 处文档的版本表述。

## 理由

**为什么不保留 3.8 支持**：

- Python 3.8 已于 **2024-10 EOL**，不再有安全更新。在一个要发给 NAS 用户用的
  工具里宣称支持一个无安全维护的版本，反而是害用户。
- 保留 3.8 的唯一技术路径是**放弃 `license-files`**，退回
  `license = {text = "MIT"}` 旧写法——但 setuptools 已明确该写法
  **2027-02-18 后不再支持**。等于把一个即将到来的硬期限换成另一个。
- 真正的 3.8 用户群极小：NAS 上装 Python 本来就费劲（群晖的 Python 版本杂），
  而这类用户更可能用 3.9+ 的系统 Python 或 Docker。

**为什么不为了 3.8 保留而把整个打包链路退回旧写法**：为了 0.1% 的用户
承担「两年后必然要再做一次迁移」的成本，不划算。

## 顺带修掉的另一个问题：CI 冒烟不该断言退出码

`nastool` 的退出码语义是 **0 健康 / 1 有严重问题 / 2 错误**。
CI 脚本最初写成：

```yaml
python -m nastool ... -o json --output-file report.json   # 退出码非 0 就失败
```

这是**误用了工具的契约**。CI runner 上检测出任何 FAIL 项（比如权限相关的
安全检查）就返回 1 —— 那是**正常的体检结果**，不是 CI 失败。

改正后：

```yaml
python -m nastool ... || test $? -eq 1     # 0 或 1 都算跑完
python - <<'PY'                              # 断言报告内容完整
...
PY
```

**冒烟要验的是「工具能跑完并产出完整报告」，不是「这台机器很健康」。**

## 教训

1. **「声明支持某版本」是一种承诺，要用 CI 兑现。** 之前 `requires-python = ">=3.8"`
   写了两周没人发现装不上——因为本机是 3.13，从来没在 3.8 上试过。
   **声明过的组合，一个都不能漏测。**
2. **写 CI 脚本前要读工具的契约。** 退出码语义不是「成功/失败」二元，
   而是「健康/有问题/出错」三态，把 1 当失败是误用。
3. **CI 第一次跑全红是有价值的**——它一次性暴露了两个真问题，
   而这两个问题在本地全绿时完全看不见。
