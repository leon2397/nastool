# 0007. 刻意不做自动修复

- 状态：生效
- 日期：2026-10-28
- 影响：产品边界、信任模型

## 背景

前身项目做过完整的修复引擎，能力很强：能自动改 `sshd_config`、清理临时文件、调内核参数。它有一套四级风险模型，还有 `FORBIDDEN_FIXES` 禁止清单、dry-run、回滚。

**这个方向被明确放弃。** 理由是产品定位，不是技术难度。

## 决策

nastool **只诊断，不修复**。所有输出到 `suggestion` 字段为止——告诉用户「建议怎么改」，不代替他改。

具体边界：

| 允许 | 不做 |
|---|---|
| 只读采集（`sshd_config`、`/etc/exports`、`smb.conf`、证书） | 修改任何配置文件 |
| 写入测速用的临时文件（跑完删除） | 修改系统状态（服务启停、内核参数、权限） |
| 把结果 POST 到用户指定的地址 | 远程执行命令 |

唯一的写操作是测速的临时文件，写完立即删除。

## 后果

### 好处

- **信任成本大幅降低**。用户可以放心在一台生产中的 NAS 上运行，不必担心它改坏东西。这是「第三方体检报告」定位的前提
- 不需要处理回滚、并发修改、部分失败、配置语法校验、厂商差异（DSM 的 `sshd_config` 位置与语法和标准 Linux 不同）
- 不需要为「改坏了」负责。改配置的后果可能比原来的问题更严重
- 权限要求降低：只读能用非 root 跑（虽然 SMART 需要 root，但不改东西），修复必然要 root

### 代价

- **用户要自己动手**。报告指出「SSH 允许 root 直接登录」，用户得自己去改 `sshd_config`。对不熟悉 Linux 的用户来说，诊断结果可能止步于「知道自己有问题」
- 少了差异化的卖点。自动修复听起来比「只出报告」更有吸引力
- `suggestion` 的质量变得关键——既然不代劳，建议就必须足够具体可执行（「改为 `PermitRootLogin prohibit-password`」而不是「加强 SSH 安全」）

### 缓解

- 每条 WARN / FAIL 都给出具体可执行的 `suggestion`，包含具体配置项与目标值
- 不做交互式引导，但在文档里给出常见处置方式

## 为什么这条值得单独记一条 ADR

因为它是一个**被主动放弃的、看起来更有价值的功能**。

如果不写下来，未来一定会有人（包括我自己）问：「既然都能检测出来了，为什么不能顺手修掉？」然后开始加第一个「安全的」自动修复，接着是第二个、第三个，最终回到前身那条路上——而那条路的产品风险，恰恰是最高的。

诊断工具的价值在于**它是可信的**。一个会改你配置的工具，用户会先怀疑它，再考虑它的结论。这个顺序一颠倒，产品就没意义了。

## 相关

「不修复」也解释了另一个设计：**报告必须自带证据**（`evidence[]`）。既然不代劳，就得让用户能自己复核——看到 `PermitRootLogin yes` 这一行，用户才敢动手改。
