# 0004. 两条封顶规则强行压低分数

- 状态：生效
- 日期：2026-10-28（0.3.0）
- 影响：评分公信力、用户对分数的信任度

## 背景

加权平均有个致命弱点：**它会把严重问题平均掉。**

一个真实场景：某台 NAS 存储得了 95 分（13 项里 12 项通过），只有「待定扇区 8 个」这一项 FAIL。加权平均算下来 96 分 → A 级 → 「状态良好，可放心使用」。

**这块盘可能下周就挂。** 而报告告诉用户可以放心。

同类工具的典型输出就是这样：一个漂亮的总分，下面挂着一堆需要处理的问题。用户学会的第一件事是「别信那个分数，直接看问题列表」——那分数就没有存在意义了。

反过来还有一个更隐蔽的问题：一份报告可能只判定了 30% 的适用项，剩下全是 UNKNOWN（没权限、没工具、容器内）。剩下的都通过了，加权平均给 100 分。**「没查出来」被表达成了「完美」。**

## 决策

加权平均算完后，用两条规则**强行压低**：

```
规则一：存在任意 FAIL，且 总分 > 59  → 总分 = 59（D 级）

规则二：盲区 ≥ 50%，且 总分 > 74  → 总分 = 74（C 级）
       盲区 ≥ 30%，且 总分 > 84  → 总分 = 84（B 级）
```

配套三条约束：

1. **只降不升。** 本来就 45 分的报告不会因为封顶被抬到 59
2. **触发原因写入 `score.cap_reason`** 并在报告显著位置显示，不做静默降分
3. **规则二只降等级，不改退出码。** 退出码仍只看 FAIL——盲区大是「没查清」，不是「确认有故障」

## 后果

### 好处

- **分数与问题清单不可能矛盾**：有 FAIL 就必然是 D 级，不会出现「A 级但硬盘快挂了」
- **诚实表达解释力边界**：只判定了 42% 的报告拿不到 A 级，用户一眼就知道这份报告没什么说服力
- 分数变得可以用于自动化门禁——因为 A 级的含义被守住了

### 代价

- **用户会觉得「分数偏低」**。一台确实没大问题、只是跑在容器里读不到 SMART 的机器，会拿到 C 级而不是 A 级。这是刻意的：那份报告确实只能支撑 C 级的结论
- 需要向用户解释「C 级不等于有问题」。文档、报告措辞、`verdict` 文案都要照顾这一点
- 阈值（59 / 74 / 84 / 30% / 50%）是**经验值**，没有理论依据。它们代表「我认为这个程度的盲区不足以支撑这个等级」的判断

### 缓解

- 报告里明确写出触发原因：`! 57.9% 的适用项不可判定（盲区过大），等级封顶 C`
- `verdict` 文案区分「有问题」与「没查清」：C 级是「存在明显问题，建议尽快处理」，而盲区封顶会在下一行说明真实原因是盲区
- 测试锁住四条边界：`test_failure_caps_total_at_59`、`test_warn_does_not_cap`（WARN 不封顶，防过度保守）、`test_small_blind_spot_does_not_cap`、`test_unknown_does_not_deduct_category_score`

## 考虑过但否决的方案

**只做规则一（严重问题封顶），不做盲区封顶。**

否决理由：那正是 0.3.0 开发中实际撞到的问题——一份「92 分 A 级」的报告，只有 39% 覆盖率。规则一管不了这种情况，因为一项 FAIL 都没有。

**用「未判定项按 0 分算」替代盲区封顶。**

否决理由：这会把「没查到」和「查到了有问题」混为一谈，等于回到 [ADR-0001](0001-unknown-is-first-class.md) 要消除的错误。UNKNOWN 必须是中性的，它对分数的影响只能通过「降低结论的可信度」体现，不能通过「扣分」体现。

**把盲区比例直接展示，不干预分数。**

否决理由：实测过。用户只看分数，不看覆盖率那一行。不干预分数就等于允许「100 分 + 30% 覆盖率」这种组合存在，而它会被误读为「完美」。
