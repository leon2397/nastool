# 产品化规划

> **这份文档回答"nastool 作为产品要做到什么程度"，不回答"下一版改什么代码"。**
>
> 代码排期见 [VERSION-PLAN.md](VERSION-PLAN.md)——那是排期的唯一权威，本文不重复。
> 检测能力清单见 [CHECKS-ROADMAP.md](CHECKS-ROADMAP.md)，本文不重复。
> 架构与规范见 [ARCHITECTURE.md](ARCHITECTURE.md) 与 [STANDARDS.md](STANDARDS.md)。
>
> **为什么要分开**：版本计划是工程视角（一次发版改哪些文件），产品化规划是产品视角
> （这东西长成什么样、给谁用、怎么被用起来、做到哪一步算"做完了"）。两者如果混在一起，
> 会出现"版本号涨到 1.0 但产品不可用"的情况——代码完备 ≠ 产品可用。

## 〇、先说三个前提结论

这三件事决定了整份规划的形状，先摆出来，后面所有内容都是它们的推论。

### 结论一：价值主张是"结论可信"，不是"检测项多"

`nastool` 有 55 项检测，通用 NAS 体检工具也有几十项。**项数不是差异，"敢不敢照着做"才是。**

所以产品化的一切投入都指向同一件事：**让用户能验证我们给的结论，而不是要求用户相信我们。**
这条决定了后文几乎所有优先级——包括为什么"UNKNOWN 是独立状态"比"多查 10 项"更重要，
为什么"阈值来源要可查"是产品要求而不是文档洁癖。

### 结论二：成熟度止步于 L2，生态不是这条路

通用检测工具的生态价值低而维护成本高——第三方能写的检测项，主仓自己写更省事；
第三方写的检测项质量不可控，反而污染"结论可信"这条价值主张。

**所以这个产品的终点是"可被依赖"，不是"可被扩展"。** 明确承认这件事，比先许诺插件机制
再因为 `CheckContext` 一直在变而迟迟不做，要诚实得多。

对应 [Q-004](memo/open-questions.md#q-004-要不要开放第三方检测项插件) 的当前倾向：**不做**。
本文把它固化为产品战略，而不只是技术上的"暂缓"。

### 结论三：产品化最大的缺口不是功能，是"能被拿起来就用"

现在这个项目的工程质量已经不低了（55 项检测、54 项测试、12 项自检、8 条 ADR），
但**一个不懂 Python 的 NAS 用户拿到它，第一步会卡在 `pip install -e .`**。

这是典型的"工程完成度 ≠ 产品完成度"。产品化的第一优先级是把启动路径从 4 步压缩到 1 步，
而不是再加 10 项检测。

## 一、产品定位与用户

### 一句话定位

> **给 NAS 用户的可信体检**：一条命令看清一台机器的家底，给一个**能被验证的**健康结论，
> 以及一份能照着做的清单。

三个限定词都不能省：**NAS 用户**（不是通用 Linux 运维）、**能被验证**（不是自称权威）、
**能照着做**（不是只诊断不给路径）。

### 四类用户

用户画像不是编出来的，是从已有的 4 个场景（[PROFILES.md](PROFILES.md)）倒推的——
场景是"同一台机器的不同用途"，用户是"不同的人"。

| 用户 | 场景 profile | 他真正想要的 | 现在能不能满足 |
|---|---|---|---|
| **家用 NAS 拥有者** | `nas` | "这机器有没有问题？严重吗？我该干嘛？" | 结论可信 ✅ / 行动清单 ❌（DEBT-002） |
| **二手设备买家** | `verify` | "这台二手机有没有暗病？给我能当证据的东西" | 阈值更宽松 ✅ / 逐项证据 ✅ / 可导出报告 ✅ |
| **运维 / IT** | `nas` / `dev` | "接进监控，异常时能告警" | 退出码 ✅ / JSON ✅ / 协议级探测 ❌（DEBT-003） |
| **自建 / 开发者** | `dev` / `ai` | "这台机器能跑推理吗？瓶颈在哪？" | 推理实测 ✅ / 平台识别 ✅ |

### 产品不服务的用户（明确排除）

| 不服务 | 理由 |
|---|---|
| 需要自动修复的运维 | 底线二：不修改被检测设备。体检不能变成治疗（[ADR-0007](adr/0007-no-fix-engine.md)） |
| 要管 50 台设备的团队 | 那是另一个产品（凭据、并发、重试），需要时用 `ansible` 调 `nastool -o json`（[Q-005](memo/open-questions.md#q-005-要不要支持多机批量体检)） |
| 要 AI 框架清单的 | 框架列表没有边界，与设备健康无关（见 [CHECKS-ROADMAP.md](CHECKS-ROADMAP.md) 取舍说明） |
| 要资产管理系统 | `nastool` 是检测器，不是 CMDB |

## 二、用户旅程

每条旅程按"用户实际会做的事"写，不是按功能列表写。**卡点即产品化任务。**

### 旅程 A：家用 NAS 拥有者 —— "我的 NAS 是不是坏了？"

```
拿到工具 → 装上 → 跑一次 → 看懂结论 → 知道该做什么 → 下次怎么知道有没有变坏
   ⚠        ⚠         ✅        ⚠            ❌                   ⚠
```

| 阶段 | 现状 | 卡点 |
|---|---|---|
| 拿到工具 | 源码仓库，需 `git clone` + `pip install -e .` | **没有 PyPI 发布**，这是第一道墙 |
| 装上 | 需 Python 3.8+ | NAS 上不一定有 pip（群晖有但版本杂） |
| 跑一次 | `python -m nastool` 可跑 | 需 root 才读得到 SMART，普通用户拿到的报告是"大半不适用" |
| 看懂结论 | 终端报告可读，HTML 可分享 | 报告里是英文分类名 + 中文说明，混排略生硬 |
| 知道该做什么 | 有 `suggestion` 文本 | **没有优先级排序**（DEBT-002），20 项告警是 20 条并列建议 |
| 看出变化 | `--save-history` + `--compare` | 门槛三步，且从没人教过用户怎么用 |

**最刺眼的一条**：全流程唯一"有产品感"的动作是 `--list-checks`，但那是给开发者看的。

### 旅程 B：二手设备买家 —— "这台机器值不值这个价"

```
接入显示器/临时开机 → 装工具 → 跑 verify → 逐项看证据 → 导出报告当凭证
                          ⚠        ✅        ✅            ⚠
```

| 阶段 | 现状 | 卡点 |
|---|---|---|
| 装工具 | 同上 | 验机现场常常是**别人的机器、别人的系统**，安装过程可能受限 |
| 跑 verify | 场景已就绪，安全权重提到 18，阈值放宽 | 覆盖度低时报告封顶 C 级，验机方容易误读为"机器不行" |
| 逐项看证据 | `-v` 可看全部证据 | 证据是**给懂的人看的**，不是给"验机结论"看的 |
| 导出凭证 | `-o all` 出三份报告 | 报告里没有"设备身份"字段（序列号/资产编号），不能当凭证 |

**"报告能不能当凭证"是个被忽略的问题**：二手交易的争议往往就卡在这里。

### 旅程 C：运维 / IT —— "接进监控，异常告警"

```
写进 cron → 解析退出码/JSON → 异常时告警 → 定位到具体项
    ✅          ⚠                    ❌              ✅
```

| 阶段 | 现状 | 卡点 |
|---|---|---|
| 定时跑 | 退出码 0/1/2 语义清晰 | 无问题 |
| 消费结果 | JSON `report_version 3.0` 结构清晰 | 字段还会变（0.5.0 要加 `action_plan`），**没有兼容承诺**（Q-003） |
| 异常告警 | 退出码可判 | **进程活着但服务握手失败报"正常"**（DEBT-003），这类漏报最伤 |
| 定位 | 逐项证据 + 历史 diff | 历史库要手动 `--save-history`，不配 cron 参数就等于没有 |

**这一条最危险**：运维场景里，"误报"只是烦，"漏报"是事故。而 DEBT-003 描述的正是漏报。

## 三、产品形态矩阵

产品不是只有一种形态。当前只有一种半成品。

| 形态 | 目标用户 | 现状 | 达到"可交付"还差什么 | 优先级 |
|---|---|---|---|---|
| **CLI** | 全部 | ✅ 可用 | 启动路径仍需 Python 环境 | P0 |
| **单文件可执行** | 家用 / 二手 | ❌ 无 | PyInstaller 打包，目标机零 Python 依赖 | **P0** |
| **PyPI 包** | 全部 | ❌ 无（`pip install -e .` 只能本地装） | 发版流水线 + 包元数据校验 | **P0** |
| **容器镜像** | 运维 / CI | ❌ 无 | 但容器内看不到宿主机磁盘与传感器，**价值有限** | P2 |
| **库 API** | 开发者 | ⚠ 内部结构清晰但无公开承诺 | 明确"内部 API，不保证兼容" | P3 |
| **上报通道** | 运维 | ✅ webhook / ainas | 补 `--push-required`（Q-002） | P1 |
| **AINAS 集成** | 自建玩家 | ✅ 可选连接器 | 保持可选，不让它变成依赖 | 保持 |

### 三个形态设计的具体判断

**单文件可执行是性价比最高的一步。** NAS 用户最常见的形态是"拷一个文件过去跑"，
这恰好是单文件二进制的形态。但它与"零第三方依赖"存在张力：打包成单文件意味着把
Python 运行时塞进去（约 10–15 MB），这不是"引入第三方依赖"（不违反
[ADR-0006](adr/0006-zero-dependency.md)），但确实改变了体积预期。**需要实测体积后决定**——
这个决策依赖事实，不能拍脑袋，记在 [Q-011](memo/open-questions.md#q-011-要不要做单文件可执行版)。

**容器镜像的优先级要压低。** 容器里读不到宿主机的 `/sys/class/thermal`、看不到物理盘，
大部分检测项会变成 UNKNOWN。**在容器里跑体检，天然违背"结论可信"这条价值主张。**
它的正确用途是 CI 环境跑静态检查，不是生产环境体检。

**库 API 明确不承诺兼容。** 内部四层架构还会动（`CheckContext` 尤其），
对外承诺只会锁死自己。写清楚"这是内部 API"比假装稳定更省事。

## 四、成熟度阶梯

产品化不是一次性的"做完"，是逐级放权。每一级有**准出标准**——
不满足就不能进下一级，否则就是在给不可靠的东西发许可证。

| 级别 | 名称 | 含义 | 准出标准 | 当前状态 |
|---|---|---|---|---|
| **L0** | 能跑 | 开发者自己能跑 | 端到端可跑、有测试 | ✅ **已达到** |
| **L1** | 能给别人用 | 非开发者能用起来 | 见下 | ⏳ 差 3 件事 |
| **L2** | 能被依赖 | 可接进别人的系统 | 见下 | ⏳ 早期 |
| **L3** | 能长生态 | 第三方可扩展 | — | ❌ **明确不做**（见结论二） |

### L1 准出标准：能给别人用

| # | 标准 | 现状 |
|---|---|---|
| 1 | 有 LICENSE 文件 | ❌ **缺失**，README 写了 MIT 但仓库无此文件 |
| 2 | 一条命令装上（`pip install nastool` 或下载单文件） | ❌ 未发布 |
| 3 | 目标机零 Python 依赖也能跑 | ❌ 无单文件版 |
| 4 | 首次运行不因缺依赖崩溃，且明确告知缺什么 | ⚠ 部分（`--self-test` 待做，DEBT-011） |
| 5 | 报告自带设备身份，能当凭证留档 | ❌ 无设备身份字段 |

### L2 准出标准：能被依赖

| # | 标准 | 现状 |
|---|---|---|
| 1 | `report_version` 冻结，兼容策略写进 [OUTPUT.md](OUTPUT.md) | ❌ 3.0 仍在加字段 |
| 2 | 退出码语义、检测项 id、CLI 参数三者承诺不破坏 | ⚠ 已有约定，1.0 才正式承诺 |
| 3 | 至少 3 台真机验证（含 NAS / 非 NAS Linux / Windows） | ❌ 目前只在本机验证过 |
| 4 | 有一个版本计划覆盖的 0.x→1.0 完整变更记录 | ✅ [CHANGELOG.md](../CHANGELOG.md) 在写 |
| 5 | 有 CI，每次提交自动跑自检 + 测试 | ❌ **完全没有 CI** |
| 6 | 协议级探测落地，消除"端口在但服务不可用"的漏报 | ❌ DEBT-003 |

### 为什么 L2 的门槛这么高

L2 意味着别人会**基于你的结论做决策**：接进监控、改生产配置、写进验收报告。
这时候一次"漏报服务不可用"（DEBT-003）造成的损失，远大于"少支持一个平台"的损失。

**所以 L1 可以快，L2 不能抢。** 这也是 [VERSION-PLAN.md](VERSION-PLAN.md) 把 1.0 放在
0.6.0 之后、且列了 7 条硬门槛的原因。

## 五、信任机制

这是产品的核心竞争力，也是最需要持续投入的地方。**"可信"不能靠声明，只能靠让用户验证。**

### 已经做到的

| 机制 | 用户能验证什么 |
|---|---|
| 五态（含 UNKNOWN） | "读不到"不会被伪装成"正常" |
| 两条封顶规则 | 分数不会在有严重问题时虚高（[SCORING.md](SCORING.md)） |
| 覆盖度分母 = 适用项 | 不会因为平台不同而虚报盲区 |
| 多源融合 + 一致性验证 | 温度等关键读数有交叉验证，冲突会标"存疑"（[ADR-0008](adr/0008-multi-source-fusion.md)） |
| 逐项证据 + `-v` | 每条结论都能展开看依据 |
| 证据级历史 diff | 能看到"哪一项变坏了"，而不只是总分变化 |

### 还没做到的（产品化缺口）

| 缺口 | 为什么重要 | 现状 |
|---|---|---|
| **阈值来源不可查** | 用户问"为什么 85°C 才算告警"，文档说不清依据 | ❌ 阈值散在代码与 [CHECKS.md](CHECKS.md) |
| **结论不可复算** | 用户无法自己验算分数 | ❌ 报告给结果不给过程 |
| **检测项清单不完整披露** | 报告没列出"本次未检测的项" | ⚠ 有覆盖度数字，但无清单 |
| **设备身份缺失** | 报告不能当凭证 | ❌ 无序列号/资产号 |

**"阈值来源不可查"是最该补的一条。** 它直接决定用户是"参考这个工具"还是"依赖这个工具"。
补法不是加文档，而是让每个检测项能声明自己的阈值依据，让报告能打印出来。

### 一个不做的决定

**不做"参考基准"或"横向评分"。** 不给用户"你的 NAS 在同类里排第几名"——
没有可靠的大样本，横向评分就是伪科学。分数只在同一台机器的时间纵向上有意义
（[Q-006](memo/open-questions.md#q-006-跨设备的分数可以比较吗)）。

## 六、成功度量

**不下载量，不 star 数。** 一个检测工具下载 1000 次但没人用第二次，是失败。

| 层次 | 指标 | 怎么测 | 目标（1.0 时） |
|---|---|---|---|
| **被用起来** | 首次安装到跑出首份报告的成功率 | 首次运行无崩溃 + 有 `--self-test` 自诊断 | 安装后能自助跑通 |
| **被信任** | 报告中的建议被用户采纳（用户反馈） | 手动收集，无埋点 | 至少 3 个真实反馈 |
| **不误报** | 被用户判定为"误报"的项数 | 手动收集 | 单项误报率趋零 |
| **不漏报** | 用户遇到但报告说"正常"的故障数 | 手动收集 | 零容忍（DEBT-003 是重点） |
| **可维护** | 从报告到"这机器确实坏了"的时间 | 依赖清单完备度 | 无"读不到且无解释"的项 |
| **可持续** | 连续发版间隔 | git tag | 不出现超过 2 个季度无发版 |

**为什么不用埋点**：本产品承诺"默认完全离线"（[README.md](../README.md)），
加遥测会直接打破这条承诺，而这条承诺正是"拷到内网机器上也能跑"的基础设施优势。
**所有度量走手动反馈，不用数据采集。** 这是产品约束，不是能力不足。

## 七、风险登记

| # | 风险 | 概率 | 影响 | 缓解 | 触发信号 |
|---|---|---|---|---|---|
| R1 | **单人维护（bus factor = 1）** | 高 | 高 | 文档即交接物（本套 docs 体系就是为此）；ADR 记录"为什么" | 连续 2 个季度无发版 |
| R2 | **平台识别随厂商固件更新失效** | 高 | 中 | 平台判定写宽松（不精确匹配版本号）；失败时降级而非报错 | 某平台突然大面积 UNKNOWN |
| R3 | **无 CI，回归靠人工** | 高 | 中 | 12 项自检 + 54 项测试已就绪，缺的就是接进 CI | 一次本可被测试拦下的回归 |
| R4 | **无 LICENSE 法律基础缺失** | 已发生 | 高 | 补 LICENSE 文件（成本 5 分钟） | 已在本文发现 |
| R5 | **单文件打包与"零依赖"承诺冲突** | 中 | 中 | 实测体积后再定；保留纯 Python 路径 | 见 [Q-011](memo/open-questions.md#q-011-要不要做单文件可执行版) |
| R6 | **文档全中文，海外用户进不来** | 中 | 中 | 契约字段已全英文（`id`/`Status`/分类键），是刻意留的改造点 | 有非中文用户提 issue |
| R7 | **能力扩张失控（项数上瘾）** | 中 | 中 | 每个新项必须回答"它改变哪个用户决策"；否则不做 | 单版新增检测项 > 10 |
| R8 | **误报导致信任崩塌** | 低 | 高 | 关键量取最坏值 + 标存疑；宁可难看不可漏报 | 连续两次用户反馈误报 |

**R1 与 R2 是这个产品最真实的死法**：不是写不完，是没人维护 + 平台变了。
R2 尤其值得注意——13 类平台识别是差异化点，但也是维护负担。**平台判定应该宽松**，
宁可"识别为通用 Linux"也不要"识别错误"。

## 八、商业化路径

开源不等于免费提供一切。**但要先把"不靠什么赚钱"写清楚。**

### 三条路径的评估

| 路径 | 描述 | 评估 |
|---|---|---|
| **A. 纯开源 + 无服务** | 工具免费，不提供托管、不做 SaaS | ✅ **默认路径**。与"完全离线"的承诺一致，维护成本最低 |
| **B. 开源核 + 托管 SaaS** | 上传报告到云端做趋势分析 | ❌ **明确不做**。上传设备数据 = 违背隐私底线，且要养服务器 |
| **C. 开源核 + 企业版** | 批量、集中策略、SLA、审计报表 | ⚠ **保留可能性，但不排期**。等 L2 达成、且出现真实企业需求 |

### 倾向

**走 A。** 这个产品的价值来自"结论可信"，而信任的前提是"它不会把你的数据发出去"。
一旦开始上传数据，"离线可跑"这个优势就消失了，产品的核心竞争力反而被自己削弱。

**C 不是不做，是"没有需求就不做"。** 真出现企业客户时，企业版的卖点不会是"更多检测项"
（那本来就开源了），而是**集中策略 + 审计 + 责任边界**。

### 变现能力的现实评估

说实话：**这个产品的付费意愿很低。** 检测工具是"装一次、用很久"的东西，
且免费替代品不少。真正的价值可能来自：

- **与 AINAS 组合**：AINAS 是媒体 NAS，nastool 是体检工具，两者是互补的。
  "买 NAS 送体检"是一个自然的产品组合（[AINAS 连接器](../nastool/connectors/ainas.py) 已存在）
- **技术支持服务**：企业用户买的是"出事了有人管"
- **定制检测项**：某个行业客户的特定合规项（这需要插件机制，而 [Q-004](memo/open-questions.md#q-004-要不要开放第三方检测项插件) 倾向不做——**这是一处真实矛盾**，记在 [Q-012](memo/open-questions.md#q-012-插件不做与定制检测项需求怎么兼容)）

**因此：先不设商业化目标，用"被用起来"衡量。** 等有真实付费信号再谈商业模式，
而不是先设计商业模式再找用户。

## 九、行动顺序

版本计划管"哪个版本做什么"，本文管"按什么顺序达到产品目标"。两者不冲突——

### 第 0 优先：法律与分发基础（本周可做完）

| # | 事项 | 成本 | 为什么排第一 |
|---|---|---|---|
| A1 | 补 `LICENSE` 文件（MIT，README 已声明） | 5 分钟 | 法律基础缺失，其他都谈不上 |
| A2 | 补 `MANIFEST.in`，把 `reference/` 排除出构建 | 10 分钟 | 打包质量 |
| A3 | 建 GitHub 远端 + 首个 tag | 30 分钟 | 没有远端 = 没有分发渠道 = L1 无从谈起 |
| A4 | CI：每次提交跑 `selfcheck` + `pytest` | 1 小时 | R3；且这是 L2 门槛第 5 条 |

**进度**：A1 ✅（v0.3.4）· A2 ✅（v0.3.4）· A4 ✅（v0.4.0，15 格矩阵）· A3 ⏳ 待办

> A1–A4 **全部不涉及功能**，是纯粹的"产品化欠账"。它们是当前投入产出比最高的一批。

### A3 的一个坑：远端仓库不是空的

`leon2397/nastool` 这个仓库**已经存在**，且有两个分支：

| 分支 | 内容 | 处理 |
|---|---|---|
| `master` | **前身 V7.x 的完整代码**（60 项根目录、60MB，含 `docs/` `deploy/` `diagnostics/`） | **保留，不动** |
| `main` | 只有 `.gitignore` + `LICENSE` + 9 字节 README 的空壳 | 本地代码推这里 |

本地仓库与远端 `master` **历史无关**（本地从 `de67165 nastool 0.2.0` 起，
远端是 V7.2 线，`git cat-file` 查不到对方 commit），所以直接 push 会被拒绝，
而强推 `master` 会**抹掉前身的 V7.x 代码**。

**结论**：推 `main`，`master` 保持原样当作前身归档。必要时把前身的
`.github/workflows/`（V7.x 的多包 monorepo CI）保留在 `master` 上作为历史参考。
