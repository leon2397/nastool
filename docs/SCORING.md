# 评分规则与可信度

> 本文解释「这个分数怎么来的」，以及为什么它可以被信任。
>
> 相关：[CHECKS.md](CHECKS.md)（每项的判定条件）、[PROFILES.md](PROFILES.md)（场景权重为什么这样分）

---

## 1. 一句话概括

> 总分 = 各分类得分的加权平均，**然后被两条规则强行压低**——如果有严重问题，或盲区太大。

「压低」这一步是这个产品与同类工具最大的区别。大多数检测工具算完加权平均就收工，于是会出现「97 分 · A 级」下面挂着一块随时要挂的盘。

---

## 2. 三层计算

### 第一层：单条检查 → 数值

| 状态 | 折算值 | 说明 |
|---|---:|---|
| PASS | 1.0 | 正常 |
| WARN | 0.5 | 有问题但可用 |
| FAIL | 0.0 | 严重问题 |
| UNKNOWN | **不参与** | 不可判定，既不扣分也不加分 |
| SKIP | **不参与** | 不适用 |

WARN 折算 0.5 而不是 0，是因为「有问题但可用」与「坏了」之间的差距，比「正常」与「有问题」更大。

### 第二层：分类得分

对每个分类，只看**已判定项**（PASS / WARN / FAIL）：

```
分类得分 = Σ(该项权重 × 折算值) / Σ(该项权重) × 100
```

要点：

- **分母是该类已判定项的权重之和**，不是该项总数。所以某类只判定了 3 项，仍然能给出这一类自己的得分（同时报告里会标「低覆盖」）。
- **某类一项都判定不了** → 该类得分为 `null`，不参与总分计算（不是 0 分）。
- 项权重由 `@check(weight=...)` 声明，1–6，表示该项在同类里的相对重要性。`storage.smart_health` 是 6，`services.port_inventory` 是 1。

### 第三层：总分

```
总分 = Σ(分类得分 × 分类权重) / Σ(分类权重)
```

**只统计「有得分且权重 > 0」的分类。** 这意味着：

- 权重按实际参与的分类重新归一，权重和不必是 100
- 未判定（`score = null`）的分类既不贡献分子也不贡献分母
- 权重为 0 的分类（如 `verify` 场景下的 `ai`）会正常检测、正常展示，但不进总分

### 实际算一遍

一台 Windows 机器，`nas` 场景的真实输出：

| 分类 | 得分 | 权重 | 是否计入 |
|---|---:|---:|---|
| 存储 | 100 | 34 | ✓ |
| 安全 | 100 | 10 | ✓ |
| 系统与硬件 | 100 | 16 | ✓ |
| 网络 | 100 | 18 | ✓ |
| 服务与端口 | 88 | 16 | ✓ |
| 外设 | `null`（0/2 判定，全部 SKIP） | 6 | ✗ 未判定 |

```
计入权重和 = 34 + 10 + 16 + 18 + 16 = 94
加权和     = 100×34 + 100×10 + 100×16 + 100×18 + 88×16 = 9208
总分       = 9208 / 94 = 97.96 → 98
```

报告里显示 `98 分 · A 级`。注意：**外设的 6 分权重没有白白丢掉**，它只是不参与——如果外设判定了并且得了 0 分，总分会被明显拉低。

## 3. 等级

| 等级 | 分数 | 结论措辞 |
|---|---|---|
| A | ≥ 90 | 状态良好，可放心使用 |
| B | ≥ 80 | 基本可用，建议按提示优化 |
| C | ≥ 60 | 存在明显问题，建议尽快处理 |
| D | < 60 | 存在严重问题，需立即处理 |
| N/A | 无法计算 | 有效数据不足，无法给出等级 |

`N/A` 出现在所有分类都判不了的时候（例如在没有权限、依赖全缺的环境里跑）。

---

## 4. 两条封顶规则（核心）

算出来的总分会被这两条规则强行压低。**触发原因一定会写进报告的 `cap_reason` 字段，不做静默降分。**

### 规则一：存在严重问题 → 封顶 59

```
如果 存在任意一项 FAIL，且 总分 > 59 → 总分 = 59（D 级）
```

理由：一项 FAIL 意味着「需立即处理」。此时无论其他项多好，结论都不该是「状态良好」。

只有 [15 项检查](CHECKS.md#只有-15-项能产生-fail) 能产生 FAIL，所以这条规则不会滥用。

### 规则二：盲区太大 → 不给高等级

盲区 = 适用项中**不可判定**的比例。

```
如果 盲区 ≥ 50%，且 总分 > 74 → 总分 = 74（C 级）
如果 盲区 ≥ 30%，且 总分 > 84 → 总分 = 84（B 级）
```

理由：一份一半项目没测到的报告，即使剩下的都通过，也不能说「状态良好」。它最多只能算「没发现问题」。

这两条规则可以叠加，`cap_reason` 会用「；」连接，例如：

```
存在 1 项严重问题，总分封顶 59；40.0% 的适用项不可判定，等级封顶 B
```

### 封顶只降不升

规则只在「当前总分高于上限」时生效。一份本来就 45 分的报告不会因为封顶被抬到 59。

## 5. 覆盖度

覆盖度回答「这次到底判定了多少」，是可信度的另一半。

```
适用项 = 总项数 − SKIP 项数
覆盖率 = 已判定项 / 适用项 × 100%
盲区率 = UNKNOWN 项 / 适用项 × 100%
```

**分母是适用项，不是总项数。** 这个选择很关键：

在 Windows 上跑 `nas` 场景，51 项里有 31 项是 Linux 专属（SMART / RAID / inode / 温度…）标 SKIP，20 项判定。如果分母用 51，覆盖率会被算成 39.2%——看上去像「这工具在 Windows 上不好用」，但那 31 项**本来就不适用于这台机器**，不该算盲区。

用适用项作分母，覆盖率是 `20/20 = 100%`，同时报告会明确写：

> 本平台有 31 项检测不适用（多为 Linux 专属：SMART / RAID / 温度 / inode 等），结论仅基于其余 20 项

**该说的话要说，但不该用错误的数字制造焦虑。**

### 分类级「低覆盖」标记

终端和 HTML 报告里，如果某类的 `已判定 / 总数 < 50%`，会标一个「低覆盖」：

```
存储  ████████████████████ 100  权重 34  3/13 低覆盖
```

这提醒读者：这一类的 100 分只基于 3 项，不是全类都查过了。

## 6. 置信度

```
整体置信度 = Σ(已判定项权重 × 该项置信度) / Σ(已判定项权重)
```

单项置信度由检查项自己给出（读到的数据越直接、越单一来源，置信度越高），未指定时按状态取默认值：

| 状态 | 默认置信度 |
|---|---:|
| PASS | 0.90 |
| WARN | 0.85 |
| FAIL | 0.85 |
| UNKNOWN | 0.0 |
| SKIP | 0.0 |

典型取值：

| 检查项 | 置信度 | 原因 |
|---|---:|---|
| `storage.path_exists` | 1.00 | 文件系统直接回答 |
| `storage.raid_state` | 0.95–1.00 | 内核阵列状态是权威数据 |
| `security.clock_sync` | 0.85 | 走了配置文件回退路径，只能确认「已配置」 |
| `security.ssh_root_login` | 0.95 | 配置显式声明时 |
| `security.ssh_root_login`（未声明） | 0.0 | 靠默认值猜，不敢给分 |

置信度与覆盖度的分工：

- **覆盖度**说「查了多少」
- **置信度**说「查到的这些有多可靠」

两者都低才最危险：既没查几项，查到的还不可靠。

## 7. AI 能力分（独立）

`Score.ai_score` 是一个**独立展示**的 0–100 分，计算方式与总分无关：

```
基础分 60（有加速硬件）
+25（推理可用）
+15（单次推理 < 2000 ms）
上限 100
```

无加速硬件时为 0，附注「无 AI 加速硬件（纯存储用途无需关注）」。

是否进总分由场景决定：`nas` 不进，`dev` 占 10，`ai` 占 26，`verify` 权重 0（展示但不计分）。

## 8. 完整示例：封顶是怎么救回一份报告的

假设某台 NAS，`nas` 场景：

- 存储 95、安全 100、系统 100、网络 100、服务 95、外设 100
- 但 `storage.smart_bad_sectors` 报 FAIL（待定扇区 8 个）

不加封顶：加权平均约 96 分 → A 级 →「状态良好，可放心使用」。**这是骗人的。**

加了封顶：总分 59 → D 级 →「存在严重问题，需立即处理」，并附「存在 1 项严重问题，总分封顶 59」。

再假设另一台：所有判定项都 PASS，但只判定了 8/19 项（11 项 UNKNOWN）：

- 盲区率 = 11/19 = 57.9% ≥ 50%
- 加权平均 100 分 → 被压到 74 → C 级
- 附「57.9% 的适用项不可判定（盲区过大），等级封顶 C」

**结论从「完美」变成「没发现问题，但也没查出什么」——这才是诚实的表述。**

## 9. 相关代码

| 文件 | 职责 |
|---|---|
| `nastool/scoring.py` | 全部计算：分类得分、总分、两条封顶、覆盖度、置信度 |
| `nastool/profiles.py` | 分类权重与阈值 |
| `nastool/model.py` | `Score` / `Coverage` / `CategoryScore` 数据契约 |
| `nastool/checks/*.py` | 单项状态与置信度的来源 |

`scoring.py` 里没有任何具体判定逻辑——它只做算术。所有「好不好」的判断都在 `checks/` 里，这是刻意的分层，见 [ADR-0002](adr/0002-collect-does-not-judge.md)。
